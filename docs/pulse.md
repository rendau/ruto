# Интеграция с pulse

[pulse](https://github.com/rendau/pulse) — каталог сервисов и их состояния для агентов и
дежурных. ruto подключён к нему двумя способами, и оба — **только через core**: в шлюзы pulse
не ходит, всё о шлюзах core знает из их отчётов (heartbeat раз в 30 с) и каналов уведомлений.

Оба способа живут на **служебном порту core** (`SYSTEM_PORT`, по умолчанию `3003`). Он только
для кластера: на него не ведёт ingress, и ничего на нём не проверяет вход. Поэтому всё, что он
отдаёт, должно быть без секретов.

| Путь | Что |
| --- | --- |
| `GET /healthcheck` | «процесс жив», в БД не ходит — для проб k8s |
| `GET /.well-known/pulse` | манифест по [стандарту pulse](https://github.com/rendau/pulse/blob/master/docs/service-manifest.md) |
| `GET /.well-known/pulse/status` | состояние: зависимости, показатели, запросы на изменение |
| `GET /diag/gateways` | диагностическая ручка: шлюзы и их версия конфигурации |
| `GET /routes/version`, `GET /routes` | маршруты без секретов — для своей интеграции pulse с ruto |

pulse находит манифест через k8s Service: в Service `ruto-core` должен быть порт с именем
`system` → `3003`.

## Манифест (стандартное подключение)

Код: `internal/app/core/manifest.go` (сведения о сервисе, `domain`, метрики трафика шлюзов),
зависимости — в `internal/app/core/app.go` рядом с клиентами, показатели и ручка — в
`internal/handler/system`, данные — `internal/usecase/system`. Модуль стандарта —
`internal/infra/pulsekit`: копия из репозитория pulse, **на месте не правится** (обновлять —
целиком оттуда, без `pulse_test.go`).

- **Зависимости:** `pg` (критичная), `redis` и `prometheus` — если заданы `REDIS_ADDR` и
  `PROMETHEUS_URL`. Проверки идут в фоне раз в 30 с.
- **Показатели:**
  - `gateways_online` — шлюзов на связи; ноль — `degraded`;
  - `gateways_lagging` — шлюз на связи, но на старой версии дольше 2 мин после того, как core
    увидел публикацию (`usecaseSystem.LagAfter`) — `degraded`;
  - `gateways_silent` — шлюз держит канал уведомлений, но не отчитывается дольше 3 мин —
    `degraded`. Шлюз, у которого нет ни отчётов, ни канала, считается ушедшим (так выглядит
    каждый под после выкатки) и тревоги не даёт;
  - `unpublished_changes` — есть сохранённые, но не опубликованные правки (только для сведения).
- **Запросы на изменение** (`entities`): сколько в `pending` и сколько из них дольше суток —
  только показываются, состояние core не портят.
- **Метрики:** трафик через шлюзы (rps, доля 5xx, p95) — из Prometheus по метрикам шлюза.
- **Ручка `gateways`:** по каждому шлюзу — на связи ли, версия, применил ли опубликованную,
  последний сбой. Сбой — короткой фразой (`pulsekit.DescribeText`), сырой текст ошибки шлюза
  наружу не уходит.

Тесты: `internal/app/core/manifest_test.go` — манифест без нарушений стандарта, ответ ручки по
схеме, показатели.

## Маршруты для pulse (`/routes`)

pulse по маршрутам ruto находит, какие ручки сервиса опубликованы наружу и какой у них трафик.
`/routes` отдаёт **опубликованный** снапшот, урезанный до полей маршрутизации:
`base_url`; у приложения — `id`, `name`, `active`, `path_prefix`, `exclude_from_metrics`,
`backend.url`, `backend.grpc_url`; у маршрута — `id`, `active`, `type`, `http.method`,
`http.path`, `grpc.path`. Поля копируются по списку, поэтому auth, переменные, заголовки и
query-параметры бэкенда сюда не попадают, даже когда в модели появятся новые. Из адресов
бэкенда вырезаются `логин:пароль@` и query. Форма ответа — как у прежнего снапшота
(`{"version", "data": {...}}`); `/routes/version` — дешёвая проверка, менялось ли что-то.

Тест: `internal/usecase/system/usecase_test.go` — конфигурация с секретом в каждой секретной
позиции, ни один не доходит до маршрутов.
