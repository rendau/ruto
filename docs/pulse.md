# Интеграция с pulse

[pulse](https://github.com/rendau/pulse) — каталог сервисов и их состояния для агентов и
дежурных. ruto подключён к нему двумя способами, и оба — **только через core**: в шлюзы pulse
не ходит, всё о шлюзах core знает из их отчётов (heartbeat раз в 30 с) и каналов уведомлений.

Третья связь — обратная: pulse сам блокирует атакующие адреса через REST core с ключом API
(см. «Блокировка клиентов из pulse» ниже).

Оба способа чтения живут на **служебном порту core** (`SYSTEM_PORT`, по умолчанию `3003`). Он только
для кластера: на него не ведёт ingress, и ничего на нём не проверяет вход. Поэтому всё, что он
отдаёт, должно быть без секретов.

| Путь | Что |
| --- | --- |
| `GET /healthcheck` | «процесс жив», в БД не ходит — для проб k8s |
| `GET /.well-known/pulse` | манифест по [стандарту pulse](https://github.com/rendau/pulse/blob/master/docs/service-manifest.md) |
| `GET /.well-known/pulse/status` | состояние: зависимости, показатели, запросы на изменение |
| `GET /diag/gateways` | диагностическая ручка: шлюзы и их версия конфигурации |
| `GET /routes/version`, `GET /routes` | маршруты без секретов — для своей интеграции pulse с ruto |

pulse находит манифест через k8s Service: в Service `ruto-core` должен быть порт с именем
`system` → `3003`.

## Манифест (стандартное подключение)

Код: `internal/app/core/manifest.go` (сведения о сервисе, `domain`, метрики трафика шлюзов),
зависимости — в `internal/app/core/app.go` рядом с клиентами, показатели и ручка — в
`internal/handler/system`, данные — `internal/usecase/system`. Модуль стандарта —
`internal/infra/pulsekit`: копия из репозитория pulse, **на месте не правится** (обновлять —
целиком оттуда, без `pulse_test.go`).

- **Зависимости:** `pg` (критичная), `redis` и `prometheus` — если заданы `REDIS_ADDR` и
  `PROMETHEUS_URL`. Проверки идут в фоне раз в 30 с.
- **Показатели:**
  - `gateways_online` — шлюзов на связи; ноль — `degraded`;
  - `gateways_lagging` — шлюз на связи, но на старой версии дольше 2 мин после того, как core
    увидел публикацию (`usecaseSystem.LagAfter`) — `degraded`;
  - `gateways_silent` — шлюз держит канал уведомлений, но не отчитывается дольше 3 мин —
    `degraded`. Шлюз, у которого нет ни отчётов, ни канала, считается ушедшим (так выглядит
    каждый под после выкатки) и тревоги не даёт;
  - `unpublished_changes` — есть сохранённые, но не опубликованные правки (только для сведения);
  - `blocked_clients` — активных блокировок адресов клиентов, и `blocked_clients_by_agents_24h` —
    сколько блокировок сделали агенты (ключи API: MCP, pulse) за сутки, снятые и истёкшие тоже.
    Оба только для сведения: блокировки — обычное состояние, состояние core они не портят.
- **Запросы на изменение** (`entities`): сколько в `pending` и сколько из них дольше суток —
  только показываются, состояние core не портят.
- **Метрики:** трафик через шлюзы (rps, доля 5xx, p95) — из Prometheus по метрикам шлюза.
- **Ручка `gateways`:** по каждому шлюзу — на связи ли, версия, применил ли опубликованную,
  последний сбой. Сбой — короткой фразой (`pulsekit.DescribeText`), сырой текст ошибки шлюза
  наружу не уходит.

Тесты: `internal/app/core/manifest_test.go` — манифест без нарушений стандарта, ответ ручки по
схеме, показатели.

## Маршруты для pulse (`/routes`)

pulse по маршрутам ruto находит, какие ручки сервиса опубликованы наружу и какой у них трафик.
`/routes` отдаёт **опубликованный** снапшот, урезанный до полей маршрутизации:
`base_url`; у приложения — `id`, `name`, `active`, `path_prefix`, `exclude_from_metrics`,
`backend.url`, `backend.grpc_url`; у маршрута — `id`, `active`, `type`, `http.method`,
`http.path`, `grpc.path`. Поля копируются по списку, поэтому auth, переменные, заголовки и
query-параметры бэкенда сюда не попадают, даже когда в модели появятся новые. Из адресов
бэкенда вырезаются `логин:пароль@` и query. Форма ответа —
`{"version", "data": {...}}`; `/routes/version` — дешёвая проверка, менялось ли что-то.

Тест: `internal/usecase/system/usecase_test.go` — конфигурация с секретом в каждой секретной
позиции, ни один не доходит до маршрутов.

## Блокировка клиентов из pulse

pulse блокирует атакующие адреса сам, через REST core с **ключом API**: ключ `rtk_…` создаёт
администратор в админке (Profile → API keys, имя, например, `pulse`, **область `blocklist`** —
такой ключ умеет только чёрный список и ничего больше) и кладёт в kusec pulse.
Ходить — изнутри кластера на HTTP-порт core (`/api`). Ключ на `/api` принимают только эти три
метода; всё остальное с ним — как без входа. Вызов с ключом получает ограничения агента: сеть
не шире /24 (IPv6 /48), без частных и служебных сетей, не пересекаясь с `trusted_clients`, срок
обязателен (60 с … 7 суток), продлить — не дальше 7 суток от создания блокировки, снимать
можно только блокировки агентов. Сеть, которую человек разблокировал меньше 7 дней назад, pulse
заблокировать не может (403, в `message` — когда и почему её сняли). Лимиты общие для всех
агентов (pulse, MCP): не больше 500 активных блокировок и 60 новых в скользящий час. Если
блокировку уже сделал или подтвердил человек, повторный `POST` ничего не меняет и возвращает
её как есть (200, `source: "admin"`). Подробно — [architecture.md](architecture.md#чёрный-и-белый-списки-клиентов),
таблица ограничений — [mcp-server.md](mcp-server.md#блокировка-клиентов).

Заголовок: `Authorization: Bearer rtk_…` (как на MCP-порту). Числа `int64` в ответах
grpc-gateway отдаёт **строками** (`"1795545986"`); `0` во времени — «нет» (`expires_at_unix: "0"` —
без конца, `removed_at_unix: "0"` — не снята).

**Заблокировать** (или продлить активную блокировку той же сети — конец станет более поздним из
двух, причина заменится):

```
POST /api/blocked_client
{"ip": "203.0.113.7", "reason": "перебор паролей на /auth/login: 4000 запросов 401 за 5 мин", "duration_seconds": 86400}

200
{"id": "cc4a9dd3-79c9-41a0-8253-93de2bc08dc1", "ip": "203.0.113.7/32", "reason": "перебор паролей …",
 "created_by": "Иван (key pulse)", "source": "agent", "api_key_id": "d63983fc-…",
 "created_at_unix": "1795538786", "updated_at_unix": "1795538786", "expires_at_unix": "1795625186",
 "removed_at_unix": "0", "removed_by": "", "remove_reason": "", "active": true}
```

`ip` — адрес или сеть CIDR (`203.0.113.0/24`, `2001:db8:1::/48`), в ответе — нормализованная сеть.

**Список** (новые первыми; `with_history=true` — ещё снятые и истёкшие, последние 1000):

```
GET /api/blocked_client?with_history=true
200 {"results": [ <как в ответе выше>, … ]}
```

**Снять** (только блокировку с `source = agent`; причина обязательна):

```
POST /api/blocked_client/{id}/remove
{"reason": "ложное срабатывание: адрес партнёра"}
200 {}
```

Если pulse ошибается, человек в админке снимает все его блокировки сразу —
`POST /api/blocked_client/remove_agent_blocks {"api_key_id": "<ключ pulse>", "reason": "…"}`
(только из админки, ключом нельзя) — или удаляет ключ: его активные блокировки снимаются.

Ошибки — `{"code", "message", "fields"}`: `400 invalid_request` (неверный адрес, срок, лимит
частоты или числа блокировок агентов, снятие неактивной), `403 no_permission` (частная сеть,
доверенный клиент, сеть недавно разблокирована человеком, блокировка человека), `401 not_authorized` (ключ неизвестен или удалён, пользователь
больше не администратор). В `message` — причина словами, её можно показывать человеку.
