# Вход через шлюз (SSO с куками)

Шлюз сам проводит пользователя через вход у OpenID Connect провайдера (Keycloak, Authentik,
Zitadel, Okta, Auth0, свой `id` — любой, что выдаёт access-токен в формате JWT) и держит
токены провайдера в httpOnly-куках. Бэкенд по-прежнему получает `Authorization: Bearer …`,
проверка токена на каждом запросе — обычный метод авторизации `jwt`.

Фронт входит через брокер: для фронта шлюз сам — OpenID Connect провайдер, фронт входит в
него стандартным SDK (keycloak-js, oidc-client-ts, auth-js) и получает токены ruto, подписанные
ключом шлюза; провайдер видит только клиент шлюза. См. «Брокер для фронтов». Под брокером —
одна сессия шлюза в куках: брокер выдаёт фронтам токены поверх неё. Своих маршрутов входа,
обновления и выхода, кроме брокера, у шлюза нет.

Принципы:

- **Шлюз без состояния.** Сессий он не хранит: всё, что нужно между запросами, лежит в куках
  браузера. Redis (если задан) нужен только, чтобы склеивать одновременные обновления сессии
  и обмены между подами и отмечать погашенные коды входа брокера, — горячий путь без обмена в
  него не ходит.
- **Только стандарт.** Вход — OAuth 2.0 Authorization Code с PKCE, адреса провайдера — из
  OpenID Connect Discovery, клиент представляется `client_secret_basic`, выход —
  RP-Initiated Logout с `id_token_hint`. Ничего специфичного для Keycloak в коде нет.
- **Core в пути входа не участвует**: падение core не мешает входить и обновлять сессии.

## Конфигурация

- **Провайдер — в Root** (`Root.jwt[]`): `name` (наше постоянное имя — на нём держатся куки и
  адреса входа, `issuer` можно менять), `issuer` (публичный адрес провайдера, он же `iss` в
  токенах; включает discovery и вход), `internal_url` (необязательно: адрес, по которому шлюз
  сам ходит к провайдеру внутри кластера), `public_url` (адрес шлюза для адреса возврата, по
  умолчанию `base_url` Root), `client` — клиент шлюза (`id`, `secret`, `scopes`, по умолчанию
  `openid`) и `exchange_scopes` — области, которые шлюз просит при обмене общего токена на
  токен приложения (у Keycloak — `roles`; `openid` шлюз добавляет к ним сам, чтобы токен
  обмена годился и для userinfo провайдера — Keycloak без неё отвечает на userinfo 403). При заданном `issuer` поле `jwk_url` не нужно.
  Провайдер без `issuer` — просто источник ключей для проверки токенов по заголовку.
- **Аудитория приложения** (`App.jwt[]`: `{provider, audience}`, по записи на провайдера) —
  бэкенд приложения получает не общий токен, а токен со своей аудиторией: шлюз меняет общий
  токен на него сам (см. «Токен приложения»). Без записи бэкенд получает общий токен. У
  Endpoint таких полей нет.
- **Метод `jwt`** ссылается на провайдера (`provider`), `kid` — необязательная привязка к
  одному ключу. Роль `клиент:роль` ищется только в `resource_access.<клиент>.roles`,
  `клиент:*` — любая роль этого клиента, роль без клиента — в `roles`, `role`,
  `realm_access.roles` и у любого клиента.

Вход один на все приложения — через клиент шлюза. Разные права — это роли, а не отдельный
вход; отдельный провайдер — только когда различаются источники пользователей.

## Маршруты и куки

| | |
| --- | --- |
| адрес возврата от провайдера | `/_auth/<провайдер>/callback` |
| маршруты брокера | `/_auth/<провайдер>/<клиент фронта>/…` |
| access-кука (общий токен, A) | `ruto_<провайдер>`, `Path=/` |
| refresh-кука (R) | `ruto-rt_<провайдер>`, `Path=/_auth/<провайдер>` |
| кука входа | `ruto-login_<провайдер>_<state>` (`__Host-` на https), 10 минут, своя на каждый вход |
| кука токена приложения (C) | `ruto_<провайдер>_<префикс>`, `Path=/<префикс>` (`/` в префиксе — `.`) |
| кука токена фронта (F) | `ruto-ft_<провайдер>_<клиент>`, `Path=/_auth/<провайдер>/<клиент>` |

- Все куки httpOnly, `SameSite=Lax`, `Secure` — по схеме `public_url`. Срок access- и
  refresh-куки — `refresh_expires_in` ответа провайдера (иначе сутки): кука должна жить как
  сессия, а не как токен, иначе браузер удалит её раньше, чем шлюз успеет обновить.
- Access-кука — JWT как есть (на горячем пути никакой работы). Refresh-кука — JSON с
  refresh- и ID-токеном, зашифрованный AES-256-GCM, имя куки подмешано как associated data:
  значение одной куки в другую не подложить (`authflow/sealed.go`).
- Метод `jwt` с `provider` берёт токен из `Authorization`, `auth_token` или куки: у приложения
  без аудитории — общий токен, у приложения с аудиторией — токен приложения (см. ниже).
  Принятый из куки токен middleware Auth дописывает бэкенду как `Authorization: Bearer`, если
  клиент не прислал свой; сама кука тоже уходит бэкенду. Куки `ruto-rt_…` и `ruto-login_…`
  прокси из запроса к бэкенду вырезает; `ruto-ft_…` живёт на пути брокера под `/_auth` и в
  запросы к приложениям не попадает.
- Токен самого шлюза в `Authorization` (узнаётся по `kid` ключа шлюза, без проверки подписи)
  учётными данными не считается: шлюз берёт сессию из кук и подставляет бэкенду свой токен
  вместо этого заголовка: запрос фронта с токеном ruto в заголовке доходит до бэкенда с
  токеном провайдера.
- Префикс `/_auth` зарезервирован: приложение с таким `path_prefix` и endpoint с таким
  началом `http.path` не создать.

## Токен приложения

Общий токен тонкий: клиент шлюза просит у провайдера вход без ролей приложений, иначе с
каждым приложением и правом токен растёт и перестаёт помещаться в куку. Роли бэкенд получает
в токене своего приложения — шлюз меняет на него общий токен по стандарту обмена токена
(RFC 8693) прямо в рабочем запросе:

1. **Общий токен живой и кука токена приложения из той же сессии входа** (подпись
   провайдера, в `aud` есть аудитория, до `exp` больше 10 с; тот же `sub`, что у общего
   токена, и тот же `sid` — сессия провайдера, — если он есть у обоих) — запрос проходит по
   ней, роли метода проверяются по ней, обмена нет.
2. **Её нет, истекает или она от другой сессии** (другой человек, прошлый вход, закрытая
   сессия) — обмен: `grant_type=…:token-exchange`,
   `subject_token` — общий токен, `audience` — из `App.jwt[]`, `scope` — `openid` и `exchange_scopes`
   провайдера, клиент шлюза представляется `client_secret_basic`. Полученный токен проверяется
   так же, кладётся в куку приложения и в куки всех других приложений с тем же провайдером и
   аудиторией (`Set-Cookie` в ответе, срок — до `exp` токена): одного обмена хватает всем.
3. **Общего токена нет или он истёк** — 401 с `WWW-Authenticate: Bearer error="invalid_token"`,
   даже если кука токена приложения ещё живая: токен приложения без сессии, ради которой он
   получен, никого не пускает. Фронт обновляет сессию и повторяет запрос.
4. **Провайдер отказал** — по коду ответа: `invalid_grant` / `invalid_token` (общий токен
   больше не принимается) — 401, как в шаге 3; отказ по сути (у пользователя нет доступа к
   аудитории, аудитория не разрешена; Keycloak отвечает `invalid_request`) — 403, токен без
   нужной роли — тоже 403; отказ клиенту шлюза (`invalid_client`, `unauthorized_client`) —
   ошибка настройки, в лог ошибкой и 502; провайдер недоступен — 502.

Бэкенд получает `Authorization: Bearer <токен приложения>`; кука общего токена из запроса к
нему вырезается, кука токена приложения остаётся. Токен провайдера в `Authorization` (не
токен шлюза) принимается как есть, без обмена — так ходят клиенты со своими токенами.

Одновременные обмены одного общего токена на одну аудиторию склеиваются тем же механизмом,
что обновление сессии (см. ниже): на поде — `singleflight`, между подами — Redis; ответ ещё
15 с отдаётся повторно запросам, ушедшим до того, как браузер получил куку. Выход
(`end_session` брокера) и новый вход (`callback`) гасят и куки токенов приложений.

Привязка к сессии — `apptoken.SameSession`, общая для токенов приложений и фронтов. `sid`
у Keycloak один и тот же у общего токена и у токенов обмена, не меняется при обновлении по
R и новый на каждый вход. У провайдера без `sid` токены привязаны только к человеку (`sub`):
токен другого человека не берётся, а старые C после нового входа гасит `callback`. Если
провайдер даёт токену обмена свой `sid`, отличный от общего, шлюз пишет предупреждение в лог
и меняет токен на каждый запрос.

Если в `audience` записать client_id фронта, который входит через брокер, токены фронта и
бэкенда совпадут и одного обмена хватит на обе куки (см. «Брокер для фронтов»). Бэкенду, который проверяет `azp == <свой клиент>`, токен обмена не
подойдёт: у него `azp` — клиент шлюза.

## Как идёт вход

Вход у провайдера начинает `authorization` брокера, когда у браузера нет сессии (см. «Вход
фронта и обмен кода»); отдельного адреса для этого нет.

- **Discovery.** При применении снимка шлюз читает
  `<issuer или internal_url>/.well-known/openid-configuration`, сверяет в нём `issuer` и берёт
  адреса входа, обмена кода, выхода и ключей. Серверные адреса (обмен кода, ключи) переносятся
  на `internal_url`, браузерные остаются публичными. Документ кэшируется на час
  (`oidc.MetadataTTL`), при ошибке живёт прошлый.
- **Уход к провайдеру** (`authflow.Unit.Login`) — случайные `state`, `nonce` и PKCE verifier и
  адрес, куда вернуться (тот же запрос `authorization`), — в куку входа, браузер уходит к
  провайдеру клиентом шлюза (`code_challenge` S256). У каждого входа своя кука, имя — с его
  `state`: два входа сразу в двух вкладках друг другу не мешают, `callback` находит свою куку по
  `state` из ответа провайдера и гасит только её. Параметры фронта `prompt`, `max_age`,
  `login_hint`, `ui_locales`, `acr_values` передаются провайдеру как есть.
- **`GET /_auth/<провайдер>/callback`** (`authflow.Unit.Callback`) — сверяет `state`, меняет код
  на токены, проверяет ID-токен (подпись ключом провайдера, `iss`, `aud`/`azp` — наш клиент,
  `exp`, `nonce`; без ID-токена вход отклоняется) и access-токен (подпись, `iss`, `exp`), ставит
  access- и refresh-куку, гасит куки C всех приложений провайдера (они могли остаться от
  прошлого входа — другого человека или закрытой сессии) и уводит обратно на запрос
  `authorization`, который теперь находит сессию и выдаёт фронту код.
- **Ошибка входа уходит на фронт стандартным ответом**: на `redirect_uri` фронта с `error`,
  `error_description`, `state` и `iss` (в `query` или `fragment`, как просил фронт) — код
  провайдера как есть (`access_denied`, `login_required`, …), `invalid_grant` и прочие отказы
  обмена кода, `temporarily_unavailable` — провайдер недоступен, свои `state_mismatch` и
  `invalid_token`. Код не из `[A-Za-z0-9_.-]` или длиннее 64 символов заменяется на
  `server_error`. Запрос фронта из куки входа проверяется заново (адрес под брокером этого
  провайдера, адрес возврата по маскам), без куки входа вернуть некуда — ответ текстом на шлюзе.
- **Выход** — `end_session` брокера (см. «Обновление, userinfo и выход»): гасит куки и уводит на
  адрес выхода провайдера с `id_token_hint`, это закрывает всю SSO-сессию провайдера.
- **Адреса возврата фронтов** — на `public_url` шлюза или на origin из `cors.allow_origins` —
  точный или шаблоном поддомена (`https://*.example.com`); `*` здесь не считается, иначе был бы
  открытый редирект. Проверка общая с CORS — `rootModel.OriginMatcher`.

## Обновление сессии

Внутри обычного запроса шлюз сессию не обновляет — для этого refresh-токен ездил бы с каждым
запросом. Фронт обновляет токены ruto в ручке `token` брокера, и заодно по R обновляется
сессия (`authflow.Unit.Session`/`FreshSession`, см. «Обновление, userinfo и выход»).

- **Обновление по R.** Провайдер, не приславший новый refresh- или ID-токен, оставляет прежний;
  присланный ID-токен проверяется как при входе (кроме `nonce`) и должен быть с тем же `sub`,
  иначе — провайдер «недоступен». Сессии нет (нет куки, не расшифровалась, провайдер ответил
  `invalid_grant`) — куки при этом **не гасятся**: параллельное обновление из другой вкладки
  могло только что поставить свежие. Провайдер недоступен — куки не трогаются.
- **Склейка одновременных обновлений.** Несколько вкладок с одним refresh-токеном идут к
  провайдеру одним запросом: внутри пода — `singleflight`, между подами — блокировка и общий
  ответ в Redis (`oidc/shared.go`, ключ — sha256 от адреса, клиента и токена). Ответ ещё 15 с
  (`oidc.RefreshGrace`) отдаётся повторно на тот же токен — для запросов, ушедших до того, как
  браузер получил новые куки. Без Redis или при его сбое — склейка только внутри пода. Поэтому
  ротацию refresh-токенов в Keycloak («Revoke Refresh Token») можно включать.

## Брокер для фронтов

Шлюз — OpenID-провайдер для фронтов, стоящий перед настоящим провайдером (как к этому
пришли — [sso-broker-plan.md](sso-broker-plan.md)): discovery, ключи, вход фронта
(`authorization`), обмен кода и обновление токенов (`token`), userinfo, выход (`end_session`).

- У каждого фронта свой адрес: `<public_url>/_auth/<провайдер>/<клиент>` + путь `issuer`
  провайдера. Keycloak `http://kc/realms/corp` → для фронта `crm` issuer
  `https://api/_auth/corp/crm/realms/corp`, discovery — на нём же
  `/.well-known/openid-configuration`. Списка фронтов нет: годится любое имя клиента из
  латиницы, цифр и `._~-`, кроме `callback` (адрес возврата от провайдера) и `logged-out`.
- Discovery — копия документа провайдера: `issuer` и пути ручек (`authorization`, `token`,
  `userinfo`, `end_session`, `jwks_uri`) — под адресом фронта; поддерживается только
  Authorization Code + PKCE S256 для публичного клиента (`token_endpoint_auth_methods_supported:
  none`), `response_mode` `query`/`fragment`, ID-токены ES256. Из документа провайдера берутся
  только описания пользователя и страниц (`scopes_supported`, `claims_supported`,
  `subject_types_supported`, локали, ссылки на политики) — остальное (интроспекция,
  регистрация, device flow…) брокер не делает и не объявляет.
- `jwks_uri` отдаёт только ключи ruto: фронт проверяет ими токены ruto. Ключ — ES256, `kid` —
  отпечаток ключа (RFC 7638). Без ключа — 503. Discovery и JWKS — `Cache-Control: public,
  max-age=300`.
- Прочие пути под адресом фронта: `GET` без токена ruto в `Authorization` — перенаправление на
  тот же путь у провайдера (страницы аккаунта, регистрации, на которые ссылается SDK);
  остальное — 404, сам адрес фронта без пути — тоже 404. Discovery провайдера не прочитать — 502.

- Ограничения (видны в наборе проверок OpenID Foundation, план «Config» — единственный
  применимый): ID-токены только ES256 (OpenID Connect Core §15.1 требует ещё RS256); серверный клиент,
  который сам меняет код на токены, не войдёт — ручка токенов находит сессию по кукам браузера,
  по той же причине к брокеру не применимы планы набора, кроме «Config».

### Вход фронта и обмен кода

- `authorization` (GET или POST): `client_id` равен клиенту в адресе, `redirect_uri` —
  абсолютный адрес без фрагмента на origin шлюза или из `cors.allow_origins` (`*` не в счёт);
  иначе — страница ошибки 400 без перехода. Дальше ошибки уходят на адрес фронта по стандарту
  (`error`, `error_description`, `state`, `iss` по RFC 9207), в `query` или `fragment`
  (`response_mode`, у keycloak-js по умолчанию `fragment`). Обязательны `response_type=code` и
  PKCE `S256`.
  - Живая сессия шлюза (кука A; истёк A — обновление по R, `authflow.Unit.Session`) — сразу
    код ruto, без формы. `prompt=none` без сессии — `error=login_required`.
  - `max_age`: вход старше `max_age` секунд или неизвестного времени (`auth_time` провайдер не
    прислал) — как без сессии, человек вводит пароль заново; с `prompt=none` —
    `login_required`. Не число или меньше нуля — `invalid_request`.
  - Без сессии или с `prompt=login` — сам `authorization` уводит браузер к провайдеру клиентом
    `ruto` (см. «Как идёт вход»), а `callback` возвращает его на тот же `authorization` без
    `prompt` и `max_age` (иначе вход повторялся бы по кругу). Провайдер получает `prompt`,
    `max_age`, `login_hint`, `ui_locales`, `acr_values` фронта как есть; при живой сессии
    `login_hint`, `ui_locales` и `acr_values` ни на что не влияют. Неудачный вход сразу уходит на
    адрес фронта стандартным `error`.
- Код ruto — запись (адрес возврата, PKCE challenge, `nonce`, `scope`, `sub`, `auth_time`, срок
  60 с, случайный id), зашифрованная ключом refresh-куки с привязкой к провайдеру и фронту:
  нигде не хранится, открывается на любом поде, для другого фронта не открывается. С Redis
  погашенный код отмечается (`SET NX`, `ruto:gw:used:*`) и второй раз не проходит; без Redis
  повтор в пределах 60 с сдерживает только PKCE.
- `token`, `grant_type=authorization_code`: `client_id` (иначе `invalid_client`), код, тот же
  `redirect_uri`, `code_verifier`; живая сессия того же `sub`. Токен фронта F — из куки
  `ruto-ft_<провайдер>_<клиент>` (`Path=/_auth/<провайдер>/<клиент>`), если он живой, для этого
  клиента и из текущей сессии входа (тот же `sub` и `sid`, что у A, — `apptoken.SameSession`;
  F, оставшийся от прошлого входа того же человека, не берётся); иначе обмен A под `audience=<клиент>`, F кладётся в эту куку и
  копиями — в куки C приложений с `audience=<клиент>` (вход фронта сразу готовит токен его
  бэкенда). Обратно тоже: обмен в горячем пути для аудитории X кладёт копию в куку F фронта X.
  Провайдер отказал в обмене по сути (у человека нет ничего в этом фронте) — вход всё равно
  проходит, данные — из A, без ролей фронта; бэкенд потом откажет по правам. Ошибки — по RFC
  6749 §5.2 (`invalid_grant` — код, verifier, адрес, сессия; `invalid_client` — чужой
  `client_id`); провайдер недоступен — 503 `temporarily_unavailable`.
- Ответ — токены ruto, подписанные ключом ruto: ID-токен (`iss` фронта, `sub`, `aud`=`azp`=
  клиент, `nonce`, `auth_time`, данные человека из F без служебных полей провайдера),
  access-токен (те же данные с ролями — keycloak-js читает роли из него, `typ=Bearer`, `scope`)
  и refresh-токен (`typ=Refresh`, срок — до конца сессии R); `expires_in` и срок ID- и
  access-токена — до истечения A. Шлюз эти токены за учётные данные не принимает: в рабочем
  запросе берёт куки, а бэкенду отдаёт C или A вместо токена ruto в заголовке.
- keycloak-js: `checkLoginIframe: false` обязателен — iframe статуса входа и проверка сторонних
  кук ходят к самому провайдеру, брокер за него их не отвечает. Сам keycloak-js шлёт куки в
  ручку токенов (`credentials: 'include'`), а `loadUserInfo()` — нет, поэтому через брокер он
  не работает (сам keycloak-js userinfo не зовёт: профиль и роли он берёт из токенов);
  oidc-client-ts — с `fetchRequestCredentials: 'include'`, в auth-js такой настройки пока нет
  (расширение из плана). При открытии страницы keycloak-js с `check-sso` идёт на
  `authorization` с `prompt=none` — переход виден, но провайдер не участвует.
- Фронт во встроенной рамке (оболочка с приложениями на своих поддоменах): при живой сессии
  входит как обычно — oidc-client-ts через userinfo, keycloak-js через `prompt=none` в рамке
  (шлюз показ своих ручек в рамке не запрещает), и обновляет токены там же. Страница входа
  провайдера в рамке не показывается (Keycloak запрещает), поэтому вход без сессии делает
  оболочка на верхнем уровне — сама как фронт брокера — и перезагружает рамки. Выход из рамки через брокер работает (цепочка переходов до
  провайдера и обратно страниц провайдера не показывает).

### Обновление, userinfo и выход

- `token`, `grant_type=refresh_token`: важна сессия в куках, а не refresh-токен ruto. Из него
  берутся только `sub` (должен совпасть с сессией — человек не сменился в другой вкладке) и
  `scope`; подпись не проверяется, поэтому токен, выданный до смены ключа, тоже годится, но
  `iss` должен быть этого фронта. Общий токен A обновляется по R, если от его срока осталось
  меньше половины (`authflow.Unit.FreshSession`; иначе SDK, которому токены ruto живут до
  истечения A, обновлялся бы сразу снова), склейка обновлений — как в рабочем пути. Ответ —
  новые токены ruto со сроком до нового A, ID-токен с теми же `sub`, `azp`, `auth_time` и без
  `nonce` (oidc-client-ts сверяет их с прежним, keycloak-js без ID-токена в ответе его
  теряет). F берётся из куки или обменом. Нет сессии — `invalid_grant`, SDK уходит на вход.
- `userinfo` с токеном ruto в `Authorization`: токен должен быть токеном ruto этого фронта и
  того же человека, что сессия (иначе 401 `WWW-Authenticate: Bearer error="invalid_token"`);
  шлюз берёт F (кука или обмен; при отказе в обмене — A) и спрашивает userinfo провайдера по
  его внутреннему адресу, ответ отдаёт как есть. Истёкший A при живом R сначала обновляется.
- `userinfo` без токена (открытие страницы, расширение auth-js из плана): сессия по кукам, к
  ответу провайдера добавляется объект `tokens` — access- и refresh-токен ruto для фронта,
  `token_type`, `expires_in` (без ID-токена: входа с `nonce` не было). Нет сессии — 401
  (`WWW-Authenticate: Bearer`), SDK идёт на обычный вход. Ответы userinfo — `Cache-Control:
  no-store`; прочитать их скрипт может только с сайтов из `cors.allow_origins` с
  `allow_credentials`.
- Keycloak собирает userinfo без учёта аудитории токена: mapper ролей в userinfo отдал бы роли
  всех клиентов, поэтому у Keycloak роли фронта берутся из токенов ruto (в них роли из F, где
  Keycloak оставил только роли клиента фронта), а userinfo — только данные человека. Провайдер,
  который отдаёт в userinfo роли по аудитории токена (auth по плану), отдаст фронту его роли.
- `end_session` (GET или POST): `post_logout_redirect_uri` проверяется как адрес возврата при
  входе (без него — корень шлюза), чужой `client_id` — 400. Гасятся A, R, F этого фронта и куки
  C всех приложений со своей аудиторией, браузер уходит через `end_session_endpoint`
  провайдера с ID-токеном провайдера из R (`id_token_hint` фронта не нужен) и адресом возврата
  фронта (у клиента `ruto` в провайдере должны быть разрешены адреса фронтов); `state`
  передаётся провайдеру, а без выхода у провайдера добавляется к адресу самим шлюзом. Куки F
  других фронтов погасить нельзя — их имён шлюз не знает, — но после выхода они не
  используются: без сессии их SDK получат `invalid_grant` и уйдут на вход, а после нового
  входа (даже того же человека) у F старый `sid`, и брокер меняет A на новый F.

## Настройки шлюзов от core

Redis для склейки, ключ шифрования refresh-куки и ключ подписи токенов ruto шлюзы получают от
core вместе со снимком (`Snapshot.Get`, поле `gateway`); в БД, админку и MCP они не попадают.

- Redis: env core `GW_REDIS_ADDR`, `GW_REDIS_DB`, `GW_REDIS_PASSWORD`; без `GW_REDIS_ADDR` —
  Redis самого core (`REDIS_*`); нет ни того, ни другого — склейка только внутри пода.
- Ключ: HKDF-SHA256 от `GW_COOKIE_SECRET`, без него — от `ADMIN_JWT_SECRET`. Смена секрета
  разлогинивает всех из сессий шлюза (access-куки доживают свой срок). Core без ключа — шлюз
  предупреждает в логе и refresh-куку не ставит: вход работает, обновления нет.
- Ключ подписи токенов ruto (ES256): тоже HKDF от того же секрета, но со своей меткой, так что
  с ключом куки он не связан; шлюзу уходит приватный ключ (32 байта), на всех подах одинаковый.
  Смена секрета — новый ключ и новый `kid`: токены ruto, выданные раньше, не пройдут проверку.
  Тот же `kid` шлюз узнаёт в токене ruto из `Authorization` и не принимает такой токен за
  учётные данные (см. «Токен приложения»).
- Версия настроек — `settings_version` в `Snapshot.GetVersion` (HMAC ключом
  `ADMIN_JWT_SECRET`). Сменились только настройки — шлюз переподключает Redis и меняет ключи,
  не пересобирая маршруты (`gw.applySettings`).

## Что настроить у провайдера и в CORS

- Клиент шлюза — конфиденциальный («Client authentication: On»), адрес возврата
  `https://<шлюз>/_auth/<провайдер>/callback`, в «Valid post logout redirect URIs» — адреса
  фронтов.
- Роли по приложениям: приложения заведены клиентами-контейнерами ролей (вход у них
  выключен), у клиента шлюза «Full scope allowed». Тогда в токене приложения есть
  `resource_access.<приложение>.roles`.
- Обмен в Keycloak (26.2+): у клиента шлюза включён «Standard token exchange», область `roles`
  — необязательная (общий токен без ролей, шлюз просит её при обмене через
  `exchange_scopes`; `audience` оставляет в токене только роли этого приложения), а в `aud`
  общего токена есть сам клиент шлюза (mapper «Audience» с ним): Keycloak меняет только
  токены, выданные для того, кто просит обмен. Срок токена обмена в Keycloak равен сроку
  access-токена клиента шлюза — отдельно его не задать.
- Размер: лимит куки — 4 КБ, access-токен обычно 1–2 КБ; лишнее из токена убирать mapper'ами
  провайдера (шлюз предупреждает в логе о слишком большой куке).
- CORS: фронту, который ходит на шлюз с куками, нужны `allow_credentials=true` и его origin в
  `allow_origins` (точный или `https://*.example.com`; `*` технически работает, но тогда запрос
  с кукой пользователя может сделать любой сайт).
- Фронт и шлюз на поддоменах одного домена (`app.example.com` / `api.example.com`) — один
  «сайт» для браузера, `SameSite=Lax` достаточно.
