# Вход через шлюз (SSO с куками)

Шлюз сам проводит пользователя через вход у OpenID Connect провайдера (Keycloak, Authentik,
Zitadel, Okta, Auth0, свой `id` — любой, что выдаёт access-токен в формате JWT) и держит
токены в httpOnly-куках. Токены в браузерный JS не попадают, фронт в логине не участвует,
бэкенд по-прежнему получает `Authorization: Bearer …`. Проверка токена на каждом запросе —
обычный метод авторизации `jwt`.

Принципы:

- **Шлюз без состояния.** Сессий он не хранит: всё, что нужно между запросами, лежит в куках
  браузера. Redis (если задан) нужен только, чтобы склеивать одновременные обновления сессии
  между подами, — горячий путь в него не ходит.
- **Только стандарт.** Вход — OAuth 2.0 Authorization Code с PKCE, адреса провайдера — из
  OpenID Connect Discovery, клиент представляется `client_secret_basic`, выход —
  RP-Initiated Logout с `id_token_hint`. Ничего специфичного для Keycloak в коде нет.
- **Core в пути входа не участвует**: падение core не мешает входить и обновлять сессии.

## Конфигурация

- **Провайдер — в Root** (`Root.jwt[]`): `name` (наше постоянное имя — на нём держатся куки и
  адреса входа, `issuer` можно менять), `issuer` (публичный адрес провайдера, он же `iss` в
  токенах; включает discovery и вход), `internal_url` (необязательно: адрес, по которому шлюз
  сам ходит к провайдеру внутри кластера), `public_url` (адрес шлюза для адреса возврата, по
  умолчанию `base_url` Root) и `client` — клиент по умолчанию (`id`, `secret`, `scopes`,
  по умолчанию `openid`). При заданном `issuer` поле `jwk_url` не нужно. Провайдер без
  `issuer` — просто источник ключей для проверки токенов по заголовку.
- **Свой клиент приложения** (`App.jwt[]`: `{provider, client{id, secret, scopes}}`) —
  отдельный вход и отдельная кука у этого приложения. Без него приложение живёт на общем входе
  Root. У Endpoint полей входа нет.
- **Метод `jwt`** ссылается на провайдера (`provider`), `kid` — необязательная привязка к
  одному ключу. Роль `клиент:роль` ищется только в `resource_access.<клиент>.roles`,
  `клиент:*` — любая роль этого клиента, роль без клиента — в `roles`, `role`,
  `realm_access.roles` и у любого клиента.

Свой клиент приложению нужен, когда ему нужны свой `aud`, свой секрет или свой срок сессии.
Разные права при общем входе — это роли, а не отдельный вход; отдельный провайдер — только
когда различаются источники пользователей.

## Единица входа, маршруты и куки

**Единица входа** — провайдер со своим клиентом по умолчанию (общий вход) или приложение со
своим клиентом. У каждой — свои маршруты и куки:

| | Общий вход | Свой клиент приложения `/shop` |
| --- | --- | --- |
| маршруты | `/_auth/<провайдер>/login\|callback\|refresh\|logout` | `/_auth/<провайдер>/shop/…` |
| `me` | `GET /_auth/<провайдер>/me` | `GET /shop/_auth/<провайдер>/me` |
| access-кука | `ruto_<провайдер>`, `Path=/` | `ruto_<провайдер>_shop`, `Path=/shop` |
| refresh-кука | `ruto-rt_<провайдер>`, `Path=/_auth/<провайдер>` | `ruto-rt_<провайдер>_shop`, `Path=/_auth/<провайдер>/shop` |
| кука входа | `ruto-login_<провайдер>` (`__Host-` на https), 10 минут | так же, с `_shop` |

- `me` приложения лежит внутри его префикса, потому что его access-кука ограничена префиксом
  и до `/_auth/…` браузер её просто не довезёт.
- Все куки httpOnly, `SameSite=Lax`, `Secure` — по схеме `public_url`. Срок access- и
  refresh-куки — `refresh_expires_in` ответа провайдера (иначе сутки): кука должна жить как
  сессия, а не как токен, иначе браузер удалит её раньше, чем шлюз успеет обновить.
- Access-кука — JWT как есть (на горячем пути никакой работы). Refresh-кука — JSON с
  refresh- и ID-токеном, зашифрованный AES-256-GCM, имя куки подмешано как associated data:
  значение одной единицы входа в куку другой не подложить (`authflow/sealed.go`).
- Метод `jwt` с `provider` берёт токен из `Authorization`, `auth_token` или куки своей
  единицы входа (приложение со своим клиентом читает только свою куку, общую — нет). Принятый
  из куки токен middleware Auth дописывает бэкенду как `Authorization: Bearer`, если клиент
  не прислал свой; сама access-кука тоже уходит бэкенду. Куки `ruto-rt_…` и `ruto-login_…`
  прокси из запроса к бэкенду вырезает.
- Префикс `/_auth` зарезервирован: приложение с таким `path_prefix` и endpoint с таким
  началом `http.path` не создать.

## Как идёт вход

- **Discovery.** При применении снимка шлюз читает
  `<issuer или internal_url>/.well-known/openid-configuration`, сверяет в нём `issuer` и берёт
  адреса входа, обмена кода, выхода и ключей. Серверные адреса (обмен кода, ключи) переносятся
  на `internal_url`, браузерные остаются публичными. Документ кэшируется на час
  (`oidc.MetadataTTL`), при ошибке живёт прошлый.
- **`GET login?redirect=…[&prompt=…]`** — случайные `state`, `nonce` и PKCE verifier в куку
  входа, браузер уходит к провайдеру (`code_challenge` S256). `prompt` из OpenID Connect
  (`login` — спросить пароль заново даже при живой сессии, `select_account`, `consent`, `none`)
  передаётся как есть; что-то вне стандарта — 400.
- **`GET callback`** — сверяет `state`, меняет код на токены, проверяет ID-токен (подпись
  ключом провайдера, `iss`, `aud`/`azp` — наш клиент, `exp`, `nonce`; без ID-токена вход
  отклоняется) и access-токен (подпись, `iss`, `exp`), ставит access- и refresh-куку и уводит
  на адрес возврата.
- **Ошибка входа возвращается на фронт.** Если адрес возврата известен, шлюз уводит браузер
  туда с `auth_error=<код>` в query (фрагмент `#/…` сохраняется): код провайдера как есть
  (`access_denied`, `login_required`, …), `invalid_grant` и прочие отказы обмена кода,
  `temporarily_unavailable` — провайдер недоступен, свои `state_mismatch` и `invalid_token`.
  Код не из `[A-Za-z0-9_.-]` или длиннее 64 символов заменяется на `server_error`. Без куки
  входа вернуть некуда — ответ текстом на шлюзе.
- **`GET logout?redirect=…`** — гасит куки и уводит на адрес выхода провайдера с
  `id_token_hint` (если ID-токена нет — сразу на адрес возврата). Это закрывает всю
  SSO-сессию провайдера: куки других единиц входа останутся, но обновиться уже не смогут.
- **Адрес возврата** принимается относительный, на `public_url` шлюза или на origin из
  `cors.allow_origins` — точный или шаблоном поддомена (`https://*.example.com`); `*` здесь
  не считается, иначе был бы открытый редирект. Проверка общая с CORS — `rootModel.OriginMatcher`.

## Обновление сессии и `me`

Обновление делает фронт: получив 401, зовёт `POST …/refresh` и повторяет запрос. Внутри
обычного запроса шлюз сессию не обновляет — для этого refresh-токен ездил бы с каждым
запросом.

- **`POST refresh`** (GET — 405: кука `SameSite=Lax` не едет в межсайтовом POST, чужой сайт
  обновление не вызовет). Ответы, у всех `Cache-Control: no-store`:
  - `204` — куки обновлены. Провайдер, не приславший новый refresh- или ID-токен, оставляет
    прежний; присланный ID-токен проверяется как при входе (кроме `nonce`) и должен быть с тем
    же `sub`, иначе `502`;
  - `401` — сессии нет (нет куки, не расшифровалась, провайдер ответил `invalid_grant`). Куки
    при этом **не гасятся**: параллельное обновление из другой вкладки могло только что
    поставить свежие;
  - `502` — провайдер недоступен или отказал по другой причине, куки не трогаются.
- **Склейка одновременных обновлений.** Несколько вкладок с одним refresh-токеном идут к
  провайдеру одним запросом: внутри пода — `singleflight`, между подами — блокировка и общий
  ответ в Redis (`oidc/shared.go`, ключ — sha256 от адреса, клиента и токена). Ответ ещё 15 с
  (`oidc.RefreshGrace`) отдаётся повторно на тот же токен — для запросов, ушедших до того, как
  браузер получил новые куки. Без Redis или при его сбое — склейка только внутри пода. Поэтому
  ротацию refresh-токенов в Keycloak («Revoke Refresh Token») можно включать.
- **`GET me`** — проверяет access-куку своей единицы (не `Authorization`) так же, как при
  входе, и отдаёт payload токена как есть, JSON-объектом (`200`), иначе `401`. Шлюз ничего не
  выбирает и не переименовывает: провайдеры кладут логин и роли в разные места, а фронту бывает
  нужна своя claim (`tenant_id`). Подпись остаётся в httpOnly-куке, из одних claims токен не
  собрать.

## Настройки шлюзов от core

Redis для склейки и ключ шифрования refresh-куки шлюзы получают от core вместе со снимком
(`Snapshot.Get`, поле `gateway`); в БД, админку и MCP они не попадают.

- Redis: env core `GW_REDIS_ADDR`, `GW_REDIS_DB`, `GW_REDIS_PASSWORD`; без `GW_REDIS_ADDR` —
  Redis самого core (`REDIS_*`); нет ни того, ни другого — склейка только внутри пода.
- Ключ: HKDF-SHA256 от `GW_COOKIE_SECRET`, без него — от `ADMIN_JWT_SECRET`. Смена секрета
  разлогинивает всех из сессий шлюза (access-куки доживают свой срок). Core без ключа — шлюз
  предупреждает в логе и refresh-куку не ставит: вход работает, обновления нет.
- Версия настроек — `settings_version` в `Snapshot.GetVersion` (HMAC ключом
  `ADMIN_JWT_SECRET`). Сменились только настройки — шлюз переподключает Redis и меняет ключ,
  не пересобирая маршруты (`gw.applySettings`).

## JS SDK для фронтов

Пакет `sdk/js` (`@rendau/ruto-auth`, описание — [`sdk/js/README.md`](../sdk/js/README.md))
делает то, что иначе повторял бы каждый фронт: куки в запросах, обновление после 401 и
повтор, одно обновление на все вкладки (Web Lock), `me`, `login`/`logout`, `loginError()`
(читает `auth_error`), помощники по ролям с тем же правилом `клиент:роль`, что у шлюза.
Адаптеры для axios, ofetch и ky.

Браузерную сборку (`dist/ruto-auth.iife.js`, глобал `RutoAuth`) отдаёт сам шлюз:
`GET /_auth/ruto-auth.js` (`gw/handler/http/sdkjs`). Файл собирается в образ шлюза
(`docker/Dockerfile.gateway`), путь переопределяется env `SDK_JS_FILE`; без файла маршрут
отвечает 404. Копии gzip и brotli считаются один раз при старте, `ETag` на кодировку,
`Cache-Control: public, max-age=300, stale-while-revalidate=86400`. Версия скрипта всегда
совпадает с версией шлюза, на который ходит фронт.

## Что настроить у провайдера и в CORS

- Клиент шлюза — конфиденциальный («Client authentication: On»), адрес возврата
  `https://<шлюз>/_auth/<провайдер>/callback` (у своего клиента приложения —
  `…/_auth/<провайдер>/<префикс>/callback`), в «Valid post logout redirect URIs» — адреса
  фронтов.
- Общий вход с ролями по приложениям: у клиента шлюза «Full scope allowed», приложения
  заведены клиентами-контейнерами ролей (вход у них выключен). Тогда в токене есть
  `resource_access.<приложение>.roles`.
- Размер: лимит куки — 4 КБ, access-токен обычно 1–2 КБ; лишнее из токена убирать mapper'ами
  провайдера (шлюз предупреждает в логе о слишком большой куке).
- CORS: фронту, который ходит на шлюз с куками, нужны `allow_credentials=true` и его origin в
  `allow_origins` (точный или `https://*.example.com`; `*` технически работает, но тогда запрос
  с кукой пользователя может сделать любой сайт).
- Фронт и шлюз на поддоменах одного домена (`app.example.com` / `api.example.com`) — один
  «сайт» для браузера, `SameSite=Lax` достаточно.
