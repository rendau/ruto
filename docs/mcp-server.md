# Встроенный MCP-сервер

MCP-сервер (Model Context Protocol) для AI-агентов **встроен в процесс `core`** и работает
на отдельном порту (streamable HTTP). Агент читает конфигурацию ruto и предлагает изменения,
но:

- **секретов не видит никогда** — ни существующих, ни создаваемых;
- **ничего не меняет сам** — каждое изменение становится *заявкой*, которую человек
  применяет или отклоняет в админке (раздел «Change requests»).

Код: `internal/handler/mcp` (транспорт), `internal/usecase/changerequest` (заявки),
`internal/domain/secretref` (маскирование и источники значений), `internal/usecase/apikey`,
`internal/usecase/oauth` + `internal/domain/oauth` (вход через OAuth, см. ниже).

Включение: `MCP_ENABLED=true`, порт `MCP_PORT` (по умолчанию `5060`). Порт публикуется
наружу отдельно от `/api` — агентам можно открыть только MCP.

## Ключи доступа

- Ключ создаёт себе **администратор** в админке: Profile → API keys. Значение (`rtk_…`)
  показывается один раз, в БД хранится только sha256. Удаление ключа действует сразу.
- Ключ принимает **только MCP-порт**; основной `/api` его отвергает (там работает только
  JWT логина). Поэтому агент, даже достав ключ из своего окружения, не обойдёт маскирование
  прямым запросом к API и не сможет сам применить заявку.
- Сессия строится по живой записи пользователя: снятие админских прав или деактивация
  пользователя сразу отключает все его ключи.
- Каждый вызов инструмента заново проверяет ключ и сверяет его с ключом, которым открыта
  MCP-сессия (подменить сессию по её id нельзя).

## Вход через OAuth (коннекторы Claude)

Вместо ключа MCP-клиент может войти по OAuth 2.1: человек вписывает в клиент только адрес
MCP-сервера, клиент открывает в браузере страницу входа ruto, человек входит в админку и
нажимает «Allow». Так подключаются коннекторы claude.ai / Claude Desktop / мобильного Claude,
этот же путь умеет Claude Code. Ключи `rtk_…` продолжают работать рядом.

Включение: `MCP_OAUTH_ENABLED=true` + `MCP_PUBLIC_URL` (адрес MCP-сервера, как его видят
клиенты) + `MCP_OAUTH_ADMIN_URL` (адрес админки, там страница согласия).

- **Подключение = ключ.** Одобренное подключение (grant, таблица `oauth_grant`) ведёт себя
  как ключ того администратора, который его разрешил: те же права, маскирование и заявки
  (в заявке автор — «Claude (OAuth)»). Снятие админских прав сразу отключает и подключения.
  Список и кнопка «Disconnect» — Profile → Connected apps.
- **Пропуска.** Access-токен `rto_…` живёт `MCP_OAUTH_ACCESS_TTL`, refresh-токен `rtr_…` —
  `MCP_OAUTH_REFRESH_TTL`; при каждом обновлении выдаётся новая пара, старый refresh больше
  не принимается. Код `rtc_…` одноразовый, живёт 2 минуты, обязателен PKCE (S256). В БД
  (`oauth_token`) хранятся только sha256. MCP-сессия привязана к подключению, а не к токену,
  поэтому переживает обновление токена.
- **Регистрация клиента** (`POST /register`, RFC 7591) открыта всем — так требует протокол.
  Защита — список разрешённых адресов возврата `MCP_OAUTH_REDIRECT_URIS`: код уходит только
  на них. Адрес без пути разрешает любой путь, loopback (`localhost`, `127.0.0.1`) — любой
  порт (Claude Code слушает случайный). В БД регистрация ничего не пишет: `client_id`
  (`rtcl_…`) — подписанные данные клиента (ключ выводится из `ADMIN_JWT_SECRET`, поэтому его
  смена инвалидирует клиентов — им нужно подключиться заново).
- **Адреса на MCP-порту:** `/.well-known/oauth-protected-resource`,
  `/.well-known/oauth-authorization-server` (и `openid-configuration`), `/register`, `/token`,
  `/revoke`. Страница согласия — `<MCP_OAUTH_ADMIN_URL>/oauth/authorize` в админке.
  401 от MCP несёт `WWW-Authenticate: Bearer resource_metadata=…` — с него клиент начинает вход.
- **Сеть.** Коннекторы claude.ai/Desktop/мобильного ходят в MCP-порт **с серверов Anthropic**:
  порт должен быть доступен из интернета (сузить можно белым списком их IP), а Cloudflare
  перед ним не должен их блокировать. Claude Code ходит с машины пользователя. Админка нужна
  только браузеру пользователя.
- **Публикация лучше отдельным поддоменом** (`https://ruto-mcp.example.com`). Если MCP
  опубликован путём (`MCP_PUBLIC_URL=https://ruto.example.com/mcp`), все адреса выше
  живут под этим путём, но часть клиентов ищет метаданные в корне домена
  (`/.well-known/oauth-*/mcp`) — тогда эти пути в Ingress тоже нужно направить на MCP-порт.

## Логи

Каждый запрос на MCP-порт пишется строкой `mcp: request`: метод, путь, JSON-RPC метод
(`initialize`, `tools/call`…), статус, время, вид учётных данных (`none` / `api_key` /
`oauth`, сами значения никогда), адрес клиента (`Cf-Connecting-Ip` → `X-Forwarded-For` →
`X-Real-Ip`), `cf_ray` для поиска запроса в событиях Cloudflare и User-Agent. Отказы —
отдельно с причиной: `mcp: credential rejected` + `oauth: access token rejected` (неизвестный,
истёкший, не access-токен, подключение удалено, пользователь больше не админ),
`mcp oauth: request rejected` (код и описание ошибки OAuth). Шаги входа: `mcp oauth: client
registered`, `oauth: consent`, `oauth: tokens issued`, `oauth: connection revoked by the client`.

## Секреты

Секретными считаются: пароли basic-авторизации, ключи `api_key`, значения переменных
(`variables`), значения заголовков и query-параметров к бэкенду (`backend.headers`,
`backend.query_params`) — у root, app и endpoint. Список путей —
`internal/domain/secretref/secretref.go` (`secretPaths`), должен совпадать с методами
`Redacted()` доменных моделей.

При чтении агент видит вместо значения слепок:

```json
"DB_PASS": {"secret_ref": "app:9f3e…/variables/DB_PASS", "chars": 24}
```

При записи в секретное поле агент кладёт **источник значения**:

| Что записать | Что получится |
| --- | --- |
| слепок `{"secret_ref": …}` из того же места, без изменений | значение остаётся как было |
| слепок `{"secret_ref": …}`, прочитанный в другом месте | значение копируется оттуда (внутри core, агент его не видит) |
| `{"generate": {"format": "alnum\|digits\|hex\|base64url\|uuid", "length": 32}, "name": "tok"}` | новое случайное значение |
| `{"reuse": "tok"}` | то же значение, что сгенерировано под именем `tok` в этой же заявке |
| обычная строка | это значение как есть (для несекретного: хосты, id) |

Ссылки на секреты и сгенерированные значения раскрываются **в момент применения**: в заявке
хранятся только описания источников. Переменные можно подставлять в другие поля как
`{{NAME}}` — это делает шлюз.

Чего в MCP нет сознательно: логов запросов (в них бывают тела и персональные данные),
«тестового запроса» к эндпоинту (возвращает живой ответ бэкенда) и подстановки переменных
`Interpolate` (вклеивает секреты в строки).

## Заявки

Агент вызывает `propose_changes` с заголовком, описанием, флагом `publish` и списком
операций:

| op | Поля |
| --- | --- |
| `create_app` | `data`, необязательный `ref` (`"$orders"`) — чтобы ссылаться на новое приложение дальше |
| `update_app` | `id`, `version`, `data` — полный объект (`get_app`, отредактированный) |
| `delete_app` | `id`, `version` — вместе с приложением удаляются все его эндпоинты |
| `create_endpoint` | `app` (id или `$ref`), `data` |
| `update_endpoint` | `id`, `version`, `data` |
| `delete_endpoint` | `id`, `version` |
| `update_root` | `version`, `data` |
| `delete_seen_paths` | `data` = `{"app": "<id или имя>", "rows": [{"method": "GET", "path": "users/{id}"}]}` — строки отчёта `list_seen_paths` (`endpoint_id` не нужен: удаляется строка у любой маски приложения, которая её насчитала) |

`version` — отпечаток объекта, который вернули `get_*`/`list_*`. Если объект изменился с
момента чтения, заявка не создаётся.

`delete_seen_paths` чистит отчёт о путях точечно. При создании заявки имя приложения
заменяется его id, и каждая строка должна быть в отчёте — иначе заявка не создаётся.
Применяется вместе с остальными операциями (всё или ничего); строки, которые до применения
успели удалить из админки, просто пропускаются. Удобно класть в ту же заявку, что создаёт
точные эндпоинты для этих путей: в отчёте остаётся только то, что ещё обслуживает маска.
В админке заявка показывает удаляемые строки с числом запросов и примером пути.

**Проверка при создании.** core сразу прогоняет все операции в транзакции, которая всегда
откатывается: те же проверки, что у правки из админки (права, обязательные поля, уникальность
имени, маски), плюс сборка итогового снимка конфигурации. Ошибку агент получает сразу.

**Отпечатки.** Для каждого объекта, который заявка меняет или из которого копирует секрет,
запоминается версия. Если кто-то изменил такой объект после создания заявки, применить её
нельзя: статус `outdated`, агент пересоздаёт заявку по свежим данным. В админке это видно
до нажатия кнопки.

**Применение.** Кнопка «Apply» доступна только администратору, вошедшему в админку
(JWT-сессия; сессия по api-ключу — никогда). Все операции выполняются **в одной транзакции**
в порядке заявки, затем проверяется итоговый снимок; любая ошибка откатывает всё. Строка
заявки блокируется (`SELECT … FOR UPDATE`), двойное применение невозможно. Если отмечено
«опубликовать», после фиксации вызывается публикация; её сбой записывается в
`publish_error`, сами изменения остаются (опубликовать можно обычной кнопкой).

**Статусы:** `pending` → `applied` | `rejected` (с комментарием) | `cancelled` (отозвал
агент) | `expired` (никто не решил за `CHANGE_REQUEST_TTL`) | `outdated`.

**Чистка** — фоном раз в час: ожидающие старше `CHANGE_REQUEST_TTL` (по умолчанию 7 дней)
становятся `expired`, закрытые удаляются через `CHANGE_REQUEST_RETENTION` (30 дней). У одного
ключа не больше `CHANGE_REQUEST_MAX_PENDING_PER_KEY` (20) ожидающих заявок.

Агент видит только заявки своего ключа.

## Инструменты

| Группа | Инструменты |
| --- | --- |
| Чтение | `get_root`, `list_apps`, `get_app`, `list_endpoints`, `get_endpoint`, `get_endpoint_effective` (после наследования), `get_swagger_diff`, `list_seen_paths` (пути wildcard-эндпоинтов с `track_paths=true` с числом запросов; флаг виден в `get_endpoint`/`list_endpoints` и меняется через `propose_changes`) |
| Публикация | `get_publish_status` — опубликованная версия, версия, которую дала бы публикация сейчас, и версия каждого шлюза |
| Метрики | `get_endpoint_metrics`, `get_app_metrics` — запросы в секунду, доля ошибок, среднее время; итоги и ряд (нужен `PROMETHEUS_URL`) |
| Заявки | `propose_changes`, `get_change_request` (статус, комментарий, ошибка, id созданных объектов, «было → стало»), `list_change_requests`, `cancel_change_request` |

Правила работы для агента сервер отдаёт при `initialize` (константа `serverInstructions` в
`internal/handler/mcp/handler.go`); дублировать их в CLAUDE.md проектов не нужно.

## Конфигурация core (env)

| Переменная | По умолчанию | Описание |
| --- | --- | --- |
| `MCP_ENABLED` | `false` | поднять MCP-сервер |
| `MCP_PORT` | `5060` | порт MCP |
| `MCP_OAUTH_ENABLED` | `false` | вход через OAuth (требует `MCP_ENABLED`) |
| `MCP_PUBLIC_URL` | — | адрес MCP-сервера для клиентов (issuer и resource OAuth) |
| `MCP_OAUTH_ADMIN_URL` | — | адрес админки, где открывается страница согласия |
| `MCP_OAUTH_REDIRECT_URIS` | адреса claude.ai, claude.com, `http://localhost`, `http://127.0.0.1` | куда можно вернуть код (через запятую) |
| `MCP_OAUTH_ACCESS_TTL` | `1h` | жизнь access-токена |
| `MCP_OAUTH_REFRESH_TTL` | `720h` | жизнь refresh-токена (продлевается при каждом обновлении) |
| `CHANGE_REQUEST_TTL` | `168h` | сколько заявка ждёт решения |
| `CHANGE_REQUEST_RETENTION` | `720h` | сколько хранятся закрытые заявки |
| `CHANGE_REQUEST_MAX_PENDING_PER_KEY` | `20` | лимит ожидающих заявок на ключ |

## Подключение агента (Claude Code)

`.mcp.json` (ключ — из окружения, не строкой в репозитории):

```json
{
  "mcpServers": {
    "ruto": {
      "type": "http",
      "url": "https://ruto-mcp.example.com/",
      "headers": {
        "Authorization": "Bearer ${RUTO_MCP_API_KEY}"
      }
    }
  }
}
```

С OAuth заголовок не нужен: `"url"` без `"headers"`, Claude Code сам откроет браузер для
входа (`/mcp` → Authenticate). В claude.ai / Claude Desktop: Settings → Connectors → Add custom
connector → адрес MCP-сервера.

Типовой сценарий:

```
list_apps → get_app {"app": "orders"} → list_seen_paths {"app": "orders"}
propose_changes {"title": "Точные эндпоинты вместо orders/v1/*", "publish": true, "ops": [
  {"op": "create_endpoint", "app": "<id>", "data": {"type": "http", "http": {"method": "GET", "path": "v1/users/{id}"}}},
  {"op": "delete_seen_paths", "data": {"app": "orders", "rows": [{"method": "GET", "path": "v1/users/{id}"}]}},
  {"op": "delete_endpoint", "id": "<id wildcard>", "version": "<version>"}]}
→ человек применяет заявку в админке
get_change_request {"id": 7} → get_publish_status
```

## Что проверяет человек

Заявка показывает каждое изменение как «было → стало». Секреты описаны словами
(«secret copied from app "billing" variables.TOKEN (32 chars)», «new random secret»), но
не показаны. На что смотреть: куда копируется секрет и **куда потом уходит запрос** — секрет,
скопированный в заголовок эндпоинта с чужим `backend.url`, уйдёт на этот адрес. Это и есть
роль человека в схеме.
