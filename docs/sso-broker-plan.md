# План: шлюз как брокер OpenID Connect и токены приложений

Статус: этапы 1–2 сделаны, остальные — план. Этапы делаются по одному, по сигналу; каждый
заканчивается проверяемым состоянием. Опирается на нынешний вход через шлюз
(`docs/sso.md`): провайдер в Root, discovery, access- и refresh-куки,
обновление со склейкой, шифрование refresh-куки остаются фундаментом; что из
него заменяется — в этапе 5 «Уборка».

## Зачем

Общий вход через шлюз упёрся в размер токена. Клиенту `ruto` провайдер кладёт в
access-токен роли и права **всех** приложений, токен растёт с каждым новым
приложением и правом и перестаёт помещаться в куку (4 КБ). Большая кука к тому же
едет в каждом запросе.

Что хотим получить:

- токены провайдера живут только в httpOnly-куках, браузерный код их не видит;
- один вход на все приложения, в том числе внутри будущей оболочки (суперапа);
- токен, который получает бэкенд, маленький: только его аудитория и его права;
- фронты остаются на своих стандартных SDK (keycloak-js в bi, auth-js в mechta),
  меняется адрес провайдера в настройках и отправка кук в запросах; auth-js
  получает одно необязательное расширение — при открытии сначала спросить
  userinfo (см. «Открытие страницы без перехода»);
- ruto не знает про auth, auth не знает про ruto; всё держится на стандартах,
  провайдер заменяем (auth в mechta, Keycloak в bi).

## Идея в двух словах

1. **Общий токен тонкий.** Клиент `ruto` получает у провайдера access-токен
   пользователя без ролей приложений (A). Он лежит в куке на `Path=/`.
2. **Токен приложения шлюз получает сам, на лету.** Для приложения со своей
   аудиторией шлюз меняет A на токен этого приложения (C) по стандарту обмена
   токена (RFC 8693), кладёт его в куку на путь приложения и отдаёт бэкенду.
3. **Для фронтов шлюз — обычный OpenID-провайдер (брокер).** SDK фронта входит «в
   ruto» по Authorization Code + PKCE, получает от ruto токены ruto и живёт с
   ними как с любыми другими. Настоящие токены провайдера при этом остаются в
   куках, а с провайдером шлюз говорит от имени клиента `ruto`.

Так устроены две известные схемы: «бэкенд для фронта» (BFF — токены у сервера,
в браузере кука; черновик IETF о браузерных приложениях называет его самым
надёжным) и брокер (свой провайдер перед настоящим — так делают Keycloak при
входе через внешний провайдер, Dex, Authentik). Своё здесь одно: с фронтом брокер
говорит на стандартном OpenID Connect, поэтому SDK фронтов работают как есть;
расширение в auth-js только убирает лишний переход при открытии страницы.

## Кто что держит

- **Сам ruto:** `client_id=ruto`, его секрет, свой ключ подписи ID-токенов.
  Своих токенов у ruto нет.
- **Куки пользователя** (все httpOnly):
  - A — общий access-токен пользователя от провайдера, `ruto_<провайдер>`,
    `Path=/`. Тонкий: без ролей приложений;
  - R — refresh-токен и ID-токен провайдера, зашифрованы, `ruto-rt_<провайдер>`,
    `Path=/_auth/<провайдер>`. В рабочие запросы не попадает (решение этапа 5
    старого плана остаётся в силе);
  - C — токен бэкенд-приложения, `ruto_<провайдер>_<префикс>`,
    `Path=/<префикс>`. Своя кука у каждого приложения со своей аудиторией, в
    запрос приходит только нужная;
  - F — токен «пользователь для этого фронта», `ruto-ft_<провайдер>_<клиент>`,
    `Path=/_auth/<провайдер>/<клиент>`. Нужен для userinfo и ID-токена фронта, в
    рабочие запросы не попадает. Если у приложения `audience` равна клиенту
    фронта, F и C этого приложения — один и тот же токен в двух куках (см.
    «Один токен — во все куки»);
  - кука входа (state, PKCE, запрос фронта) — как сейчас.
- **Память SDK фронта:** токены ruto — ID-, access- и refresh-токен, подписанные
  ruto (при открытии страницы через userinfo — без ID-токена). Шлюз их почти не
  читает (см. «Решения, принятые в обсуждении»).
- **Бэкенд:** только C (или A, если у приложения своей аудитории нет).

В рабочий запрос едут A и C; R — только в ручки ruto; F — только в ручки своего
фронта.

## Сценарий целиком

Иванов, фронт cart-fe (клиент `cart-fe`), провайдер `id`.

1. SDK cart-fe (адрес провайдера в настройках —
   `https://api.mdev.kz/_auth/id/cart-fe/realms/main`) отправляет браузер на
   `authorize` ruto: `client_id=cart-fe`, адрес возврата
   `https://cart.mdev.kz/auth/callback`, `state`, `nonce`, PKCE.
2. Сессии нет (нет A и R) — ruto запоминает запрос cart-fe в куке входа и уводит
   браузер к провайдеру уже от себя: `client_id=ruto`, адрес возврата —
   `https://api.mdev.kz/_auth/id/callback`.
3. Иванов входит у провайдера, возвращается в ruto с кодом. ruto меняет код на
   токены (с секретом `ruto`), кладёт A и R в куки.
4. ruto выдаёт свой код и возвращает браузер на `cart.mdev.kz/auth/callback`.
5. SDK меняет код в ручке токенов ruto. ruto меняет A на F (`audience=cart-fe`)
   и кладёт F в куку. У приложения ruto `seller` (главный бэкенд cart-fe)
   `audience: cart-fe` — тот же токен, поэтому ruto сразу кладёт его копию и в
   куку C продавцов (`Path=/seller`). SDK получает токены ruto: ID-токен
   (`aud=cart-fe`, `nonce` cart-fe, данные пользователя из F), access и refresh.
6. auth-js вызывает userinfo ruto — ruto берёт F из куки и проксирует запрос в
   userinfo провайдера с ним (keycloak-js сам userinfo не зовёт).
7. cart-fe ходит в `/seller/...`: приходят A и C продавцов, положенный ещё на
   шаге 5, — шлюз проверяет C и отдаёт бэкенду, без обмена. cart-fe ходит и в
   `/orders/...` — у API заказов своя аудитория (им пользуются несколько
   фронтов), куки C заказов пока нет: шлюз меняет A на C заказов, отдаёт бэкенду
   и ставит куку в ответ. Когда C истекает — так же, обмен на лету; если
   аудитория C совпадает с клиентом фронта, копия заодно ложится в F.
8. Перед истечением своего access-токена SDK вызывает обновление в ручке токенов
   ruto. Срок токенов ruto равен сроку A, поэтому это и есть момент обновить A:
   ruto берёт R, обновляет A у провайдера и выдаёт SDK новые токены ruto.
   Рабочие запросы 401 не видят.
9. Иванов открывает crm в той же оболочке: SDK crm идёт на `authorize` ruto, ruto
   видит A и R и **сразу** отдаёт код — без формы и без входа у провайдера. При
   обмене кода ruto один раз меняет A на F для `crm`; у приложения ruto `crm`
   `audience: crm`, поэтому копия сразу ложится и в его куку C.
10. Иванов снова открывает cart-fe (новая вкладка, перезагрузка). Токенов в
    памяти SDK нет, но auth-js сначала делает `GET userinfo` ruto **без токена**,
    с куками. Сессия жива — ruto отвечает данными пользователя (по F) и токенами
    ruto для cart-fe; SDK берёт их и работает дальше — без перехода страницы и
    без провайдера. Ответ 401 (сессии нет) — обычный `authorize`, как в шаге 1.
    keycloak-js так не умеет и идёт на `authorize` (шаг 9) — с видимым
    переходом, но тоже без провайдера.

## Решения, принятые в обсуждении

- **Брокер, а не посредник.** Фронты входят в ruto; провайдер видит только
  клиент `ruto` с одним адресом возврата. Вход один на всё, токены приложений
  выпускает шлюз.
- **У ruto свой ключ подписи.** ID-токен фронта («для клиента cart-fe, ответ на
  его вход») может выписать только тот, у кого фронт входил, — ruto; стандарт
  требует, чтобы выписавший его подписал. Фронт получает от ruto все три токена и
  проверяет их по ключам ruto; бэкенд получает токены провайдера и проверяет по
  ключам провайдера — смешения нет.
- **Токены ruto во фронте — «муляж» для SDK.** В рабочих запросах шлюз их не
  проверяет и не использует. Польза: SDK заранее, по их сроку, вызывает
  обновление. ID-токен — обязательная часть стандарта.
- **В горячем пути проверяется C** (и A, когда нужно получить новый C).
- **Токен приложения хранится в куке, а не в кэше шлюза.** Шлюз по-прежнему
  ничего не хранит.
- **Обмен по A, а не refresh-токены на каждое приложение.** Обновить C обменом
  стоит столько же, сколько по refresh-токену, без хранения и вращения refresh на
  каждое приложение. На обмен отдаётся access-токен (Keycloak принимает только
  его), одноразовый refresh-токен обмен не трогает.
- **Один клиент провайдера — `ruto`.** Провайдер доверяет брокеру по его секрету.
  Свои клиенты входа у приложений убираются.
- **userinfo проксируется к провайдеру с токеном F.** F получается обменом один
  раз на срок жизни и лежит в куке на пути своего фронта.
- **Один токен — во все куки, которым он нужен.** Получив обменом токен для
  аудитории X, ruto кладёт его в куки C всех приложений с `audience=X` (список —
  из снимка) и в куку F фронта с клиентом X. Если в `audience` приложения
  записать client_id OIDC-клиента, которым входит его фронт (`seller` →
  `audience: cart-fe`, `crm` → `audience: crm`), токены фронта и бэкенда
  совпадают, и на обе куки хватает одного обмена. Это удобство, а не
  обязательство: при разных аудиториях всё работает как без него, только обменов
  два. Не годится для бэкенда, общего для нескольких фронтов (например API
  заказов для cart-fe и crm): у него своя аудитория. Бэкенд должен принимать
  токен с `aud`, равным client_id фронта.
- **Открытие страницы без перехода — userinfo по кукам с токенами.** userinfo
  ruto без токена в заголовке отвечает по кукам: при живой сессии — данными
  пользователя и вложенным объектом `tokens` (`access_token`, `refresh_token`,
  `token_type`, `expires_in` — как ответ ручки токенов), без сессии — 401.
  auth-js при открытии сперва спрашивает userinfo так и, получив токены, не
  уходит на `authorize`. Это расширение, а не поломка стандарта: обычный
  провайдер на userinfo без токена ответит 401, и auth-js пойдёт на вход, как
  раньше, — auth-js про ruto не знает. Токены — во вложенном объекте, чтобы не
  смешиваться с данными пользователя и полями провайдера. ID-токена в этом пути
  нет (не было входа с `nonce`): профиль SDK берёт из userinfo, ID-токен
  провайдера для выхода ruto держит в R. Тихий вход в невидимой рамке
  (`prompt=none`) рассмотрен и не выбран: нужна отдельная страница для рамки и
  разрешение показывать `authorize` в рамке.
- **У каждого фронта свой путь к брокеру:** `/_auth/<провайдер>/<клиент>/…`.
  Иначе куки F всех фронтов ехали бы в каждую ручку ruto и переполняли заголовок.
  Какой фронт спрашивает, видно из адреса — ruto-jwt для этого не нужен.
- **Адреса возврата фронтов проверяются масками `cors.allow_origins`**, как
  сейчас.
- **«Кто может входить» в приложение при обмене не проверяется.** Единственное
  отклонение: человек без доступа получит токен приложения без ролей, фронт
  покажет сообщение по списку ролей, бэкенд откажет по правам.
- **Страницы аккаунта провайдера** (ссылки из SDK) ruto перенаправляет к
  провайдеру.
- **Не поддерживаем через брокер:** сессии auth-js (`getSessions`,
  `revokeSession*`) и токены под API (`getToken({ resource })`). Пусть ломаются.
- **Лимит сессий-устройств** — отложен.
- **Кэширование ruto** подстраивается под схему входа, если мешает.

## Решения, которые нужно подтвердить

Предложения по умолчанию; поменять до начала соответствующего этапа.

1. **Адреса брокера.** `https://api.mdev.kz/_auth/<провайдер>/<клиент>` + путь
   провайдера из его `issuer`: auth — `…/_auth/id/cart-fe/realms/main`, Keycloak —
   `…/_auth/kc/crm/realms/<realm>/protocol/openid-connect/…`. Пути ручек берутся
   из discovery провайдера, ruto о Keycloak ничего не знает. Имена `login`,
   `callback`, `refresh`, `logout`, `me`, `logged-out` как имя клиента запрещены
   (заняты маршрутами шлюза).
2. **Сроки жизни.** A — 30–60 минут (срок access-токена клиента `ruto` у
   провайдера); C и F — срок токена при обмене (обычно 5 минут); токены ruto во
   фронте — до истечения A; refresh-токен ruto — до истечения сессии (R).
   Проверить на стенде, можно ли в Keycloak задать срок токена обмена отдельно от
   срока A.
3. **Настройка приложения.** Поле `jwt[]` у приложения меняет смысл: вместо
   своего клиента `{provider, client{…}}` — `{provider, audience}`. `audience` —
   строка, которую ruto передаст в обмен (в Keycloak — client_id
   клиента-контейнера ролей, в auth — client_id приложения или аудитория API).
   Нет записи — бэкенд получает A, как сейчас. Если у фронта и его бэкенда один
   клиент, в `audience` пишется client_id фронта — тогда один обмен на обе куки
   (см. «Один токен — во все куки»). На провайдере в Root —
   необязательное `exchange_scopes`: области, которые ruto просит при обмене
   (для Keycloak — `roles`, см. «Стенд»).
4. **Код входа ruto.** Зашифрованная ключом шлюза запись (клиент, адрес возврата,
   PKCE challenge, `nonce`, `sub`, срок 60 с) плюс обязательный PKCE S256. Если
   подключён Redis — погашенный код отмечается до истечения (`SET NX`), повтор —
   отказ.
5. **Ключ подписи.** ES256. Core выводит его из `GW_COOKIE_SECRET` (без него —
   из `ADMIN_JWT_SECRET`) через HKDF со своей меткой, отдаёт шлюзам в настройках
   снимка рядом с `cookie_key`; ключ входит в `settings_version`. Смена секрета —
   новые ключи, старые токены ruto перестают проходить проверку у сторонних
   библиотек; SDK заметят это только при следующем входе.
6. **Защита от подделки запросов** — `SameSite=Lax`. Достаточно, пока все фронты
   на поддоменах одного домена (`*.mdev.kz`).
7. **Выход.** Адрес возврата после выхода — как сейчас: фронт передаёт свой,
   ruto проверяет его маской и передаёт провайдеру (у клиента `ruto` в провайдере
   разрешены адреса фронтов). Альтернатива — свой маршрут
   `/_auth/<провайдер>/logged-out`, тогда у провайдера один адрес.
8. **Старые маршруты.** `/_auth/<провайдер>/login|refresh|logout` — оставить для
   простых страниц без SDK или убрать; `me` и `sdk/js` — убрать (см. этап 5).

## Что нужно вне ruto

Можно вести параллельно этапам ruto.

**auth (`mechta/auth`):**

- обмен токена RFC 8693 в ручке токенов: `grant_type=
  urn:ietf:params:oauth:grant-type:token-exchange`, `subject_token` —
  access-токен, `subject_token_type=…:access_token`, `audience` — client_id
  приложения (выдаётся его основной токен) или аудитория API (токен этого API);
  в ответе без refresh-токена, `issued_token_type=…:access_token`; объявить grant
  в `grant_types_supported`;
- обмен разрешён только клиенту `ruto` (по настройке клиента «может
  обменивать») и только для токенов, выданных ему самому;
- «Кто может входить» в целевое приложение при обмене не проверяется;
- userinfo принимает токен, полученный обменом;
- настройка клиента «многоразовые refresh-токены» (RFC 9700 требует одноразовых
  только от публичных клиентов, `ruto` — клиент с секретом);
- у клиента `ruto` в настройках ruto в zeon убрать `roles` из запрашиваемых
  областей — A станет тонким (и `attributes`, если там права).

**Стенд (Keycloak 26.4, `config/test-stand/`):**

- у клиента `ruto` включить обмен (Standard token exchange), область `roles`
  сделать необязательной; ruto просит её при обмене (`exchange_scopes`), а
  `audience` отфильтровывает роли других клиентов;
- `configure.py` — новая настройка приложений (`audience`), провайдер без `roles`
  в областях входа;
- тестовые фронты: страница на keycloak-js (как crm) и страница на auth-js (как
  cart-fe) вместо нынешних на `sdk/js`.

**auth-js (`mechta/auth`, `sdk/js`):**

- при `init()`, когда в памяти нет токенов и адрес — не колбэк входа, сперва
  `GET userinfo` (адрес из discovery) без токена, с куками; 200 с объектом
  `tokens` — собрать пользователя из токенов и профиля (у oidc-client-ts —
  `User` и `storeUser`) и не уходить на вход; 401, ошибка сети или ответ без
  `tokens` — обычный путь (`login-required` → `authorize`);
- настройка отправки кук (credentials) при инициализации, по умолчанию
  выключена — для запросов самого SDK (`fetchRequestCredentials: 'include'` у
  oidc-client-ts), в том числе этого userinfo и ручки токенов;
- поведение с обычным провайдером не меняется: на userinfo без токена он
  ответит 401.

**Фронты (при внедрении):**

- адрес провайдера в настройках окружения: `OIDC_ISSUER`, `VITE_KEYCLOAK_URL`;
- отправка кук: в cart-fe — включить credentials в настройке auth-js (см.
  выше) и `withCredentials: true` у axios-клиентов; в crm —
  `credentials: 'include'` в `apiFetch`; keycloak-js — проверить, что запросы к
  ручке токенов он шлёт с куками;
- в Keycloak и auth — убедиться, что бэкенды не проверяют `azp == <свой клиент>`:
  у токенов обмена `azp=ruto`.

## Этапы

### Этап 1. Токен приложения на лету

**Сделано.** Поведение описано в `docs/sso.md` («Токен приложения»). Что
выяснилось на стенде: в Keycloak 26.4 срок токена обмена равен сроку
access-токена клиента `ruto` (отдельно не задать, поэтому на стенде A = C =
5 минут); обмен требует `ruto` в `aud` общего токена (mapper «Audience»);
недействительный A и отказ по сути Keycloak отвечает одним `invalid_request`,
поэтому закрытая у провайдера сессия даёт 403, а не 401. Свои клиенты входа
приложений удалены без миграции — в zeon и mechtakz их не было.

Делается и проверяется на стенде с Keycloak без брокера: вход — существующий
`/_auth/<провайдер>/login`, A — тонкий.

Что меняется:

- приложение: `jwt[] = {provider, audience}` (см. решение 3), провайдер:
  `exchange_scopes`. Свои клиенты входа у приложений (старая форма `jwt[]`) и их
  единицы входа (`/_auth/<провайдер>/<префикс>/…`) уходят здесь же: перед этапом
  проверить, используются ли они в zeon и mechtakz, и решить — миграция записей
  в `{provider, audience}` или удаление;
- `oidc`: новый вызов обмена (RFC 8693, `client_secret_basic` клиентом
  провайдера). Одновременные обмены одного A под одну аудиторию склеиваются —
  на поде (`singleflight`) и между подами через Redis, тем же механизмом, что
  обновление; ключ — `sha256(token endpoint, клиент, A, audience)`;
- горячий путь для приложения с `audience`:
  1. кука C живая (подпись провайдера, `iss`, `exp`, в `aud` есть `audience`) —
     авторизация по ней, роли метода проверяются по C;
  2. C нет или истёк, A живой — обмен, проверка C, `Set-Cookie` C
     (`Path=/<префикс>`, срок — `exp` C) и копии во все куки C других приложений
     с той же `audience`, авторизация по C (копия в F — на этапе 3, когда
     появятся фронты);
  3. A нет или истёк — 401 с `WWW-Authenticate: Bearer error="invalid_token"`;
  4. провайдер отказал в обмене по сути (нет доступа, аудитория не разрешена) —
     403; провайдер недоступен — 502;
- бэкенду: `Authorization: Bearer <C>`, кука A из запроса вырезается (как сейчас
  R и кука входа), кука C остаётся;
- `Authorization` с токеном ruto (его узнаём по `kid` ключа ruto в заголовке
  токена, без проверки подписи) не считается учётными данными: шлюз берёт куки, а
  бэкенду подставляет C вместо этого заголовка. На этапе 1 токенов ruto ещё нет,
  но правило закладывается здесь;
- приложение без `audience` — как сейчас: A из куки или токен провайдера из
  заголовка; если в заголовке токен ruto — берётся A из куки, и бэкенду он
  подставляется вместо заголовка.

Где в коде: модель приложения и наследование (`internal/domain/app/model`, замена
`JwtClient`), авторизатор `jwt` и middleware auth
(`internal/service/gw/service/auth`, `internal/service/gw/handler/http/middleware`),
`internal/service/gw/service/oidc` (обмен рядом с `Exchange`/`Refresh`, склейка в
`shared.go`), имена кук — `internal/constant`. Proto, DTO, админка (поле
`audience` у приложения вместо клиента входа), MCP.

Точка проверки: вход через общий клиент → A без ролей; запрос в `/orders/hello` →
обмен, бэкенд получает токен с `aud=orders` и ролями только orders, в браузере
кука `ruto_corp_orders` на `Path=/orders`; повтор — без обмена; через срок C —
новый обмен; пользователь без ролей orders — 403; три одновременных запроса — один
обмен.

### Этап 2. Брокер: discovery и ключи

**Сделано.** Поведение описано в `docs/sso.md` («Брокер для фронтов»). Из документа
провайдера копируются только описания пользователя и страниц (белый список), а не
всё, что «не противоречит»; ручки брокера до этапов 3–4 отвечают 404, чтобы
`authorize` фронта не ушёл к провайдеру напрямую. `kid` — отпечаток ключа
(RFC 7638).

Что меняется:

- core выводит ключ подписи и отдаёт его шлюзам в настройках снимка (решение 5);
- шлюз отдаёт на `/_auth/<провайдер>/<клиент>/<путь issuer провайдера>/.well-known/openid-configuration`
  копию discovery провайдера: `issuer` — свой адрес для этого фронта;
  `authorization_endpoint`, `token_endpoint`, `userinfo_endpoint`,
  `end_session_endpoint`, `jwks_uri` — пути провайдера под своим адресом;
  `grant_types_supported` — `authorization_code`, `refresh_token`;
  `code_challenge_methods_supported` — `S256`; `response_modes_supported` —
  `query`, `fragment`; `token_endpoint_auth_methods_supported` — `none`;
  остальное — из документа провайдера, если не противоречит;
- JWKS ruto по своему `jwks_uri` — только ключи ruto, со своим `kid`;
- прочие пути под адресом брокера: `GET` без токена ruto — перенаправление на тот
  же путь у провайдера (страницы аккаунта, регистрации); остальное — 404.

Где в коде: `snapshotModel.GatewaySettings`, `usecase/snapshot`,
`gw.applySettings`; новый пакет брокера рядом с `authflow`
(`internal/service/gw/handler/http/broker`), маршруты регистрируются там же, где
`authflow`.

Точка проверки: discovery для `crm` и `cart-fe` отдаёт разные `issuer` и свои
адреса; JWKS проходит проверку стандартной библиотекой; ссылка
`…/_auth/id/cart-fe/account/profile` уводит на страницу провайдера.

### Этап 3. Брокер: вход и обмен кода

Что меняется:

- `authorize`: `client_id` должен совпадать с клиентом в адресе;
  `response_type=code`; обязательный PKCE S256; адрес возврата — по маскам
  `cors.allow_origins`; `response_mode` `query` или `fragment` (у keycloak-js по
  умолчанию `fragment`);
  - живая сессия (A или R) и не `prompt=login` — сразу код ruto (при истёкшем A —
    сначала обновление по R);
  - `prompt=none` без сессии — возврат на фронт с `error=login_required`;
  - иначе — существующий вход у провайдера клиентом `ruto`; запрос фронта едет в
    куке входа; `prompt=login` передаётся провайдеру; после возврата — A, R и код
    ruto на адрес фронта; ошибка входа — на адрес фронта со стандартным
    `error` (как сейчас `auth_error`, но по стандарту);
- ручка токенов, `grant_type=authorization_code`: код (решение 4), совпадение
  адреса возврата и клиента, PKCE verifier; F — из куки, если живой и того же
  `sub`, иначе обмен A под `audience=<клиент>` и кука F (и копии в куки C
  приложений с `audience=<клиент>`; обратно — обмен в горячем пути кладёт копию
  в F фронта с клиентом, равным `audience`); ответ — ID-токен ruto
  (`iss` фронта, `sub`, `aud=<клиент>`, `azp`, `nonce`, `auth_time`, `iat`, `exp`,
  данные пользователя из F без служебных полей), access- и refresh-токен ruto
  (JWT с `exp`/`iat`: keycloak-js разбирает оба), `token_type=Bearer`,
  `expires_in`;
- ошибки ручки токенов — стандартные (RFC 6749 §5.2): `invalid_grant`,
  `invalid_request`, `unsupported_grant_type`.

Где в коде: пакет брокера; общий с `authflow` вход у провайдера (кука входа,
`callback`, `setSession`), `oidc` — обмен.

Точка проверки: страница на keycloak-js входит через ruto (вход в Keycloak, возврат,
токены у SDK, `nonce` сошёлся); вторая страница на auth-js в том же браузере входит
без формы; повтор кода — отказ (с Redis); чужой адрес возврата — отказ; у
приложения с `audience`, равной клиенту фронта, вход фронта ставит и F, и C, а
первый рабочий запрос идёт без обмена.

### Этап 4. Брокер: обновление, userinfo, выход

Что меняется:

- ручка токенов, `grant_type=refresh_token`: содержимое refresh-токена ruto не
  важно, важна кука R; A при необходимости обновляется у провайдера (склейка —
  как сейчас), новые куки, новые токены ruto со сроком до нового A, F — при
  истечении обменом; нет сессии (`invalid_grant` у провайдера, нет R) —
  `invalid_grant`, SDK уходит на вход;
- userinfo: F из куки (при истечении — обмен A, новая кука), проксирование в
  userinfo провайдера (по `internal_url`) с F, ответ как есть; A нет или истёк —
  401 с `WWW-Authenticate: Bearer error="invalid_token"`; F используется только
  при живой сессии и том же `sub`, что в A;
- userinfo **без токена в заголовке** (открытие страницы): сессия по кукам; A
  истёк, а R живой — сначала обновление A по R (склейка — как сейчас); к ответу
  провайдера добавляется объект `tokens` с токенами ruto для этого фронта (срок
  — до истечения A); нет сессии — 401. Ответ — `Cache-Control: no-store`;
  прочитать его скрипт может только с сайтов из `cors.allow_origins` с
  `allow_credentials`, а сами токены ruto без кук ничего не дают;
- выход (`end_session`): гасятся A, R, F этого фронта и куки C всех приложений со
  своей аудиторией (пути известны из снимка); уход на `end_session_endpoint`
  провайдера с его ID-токеном из R (решение 7). Куки F других фронтов остаются,
  но без живой сессии не работают и доживают свой срок.

Точка проверки: обе тестовые страницы живут дольше срока A без 401 в рабочих
запросах; auth-js получает роли фронта из userinfo; перезагрузка страницы на
auth-js при живой сессии — без перехода на `authorize` и без запросов к
провайдеру (кроме обмена или обновления, если истёк F или A); без сессии — 401 и
обычный вход; выход в одном фронте → второй при следующем обновлении уходит на
вход.

## Что ломается и отклонения

- auth-js через брокер: `getSessions`, `revokeSession*`, `getToken({ resource })`
  не работают (принято);
- «Кто может входить» в приложение не проверяется при обмене (принято);
- лимит сессий-устройств: у провайдера одна сессия клиента `ruto`, а не по
  сессии на фронт (отложено);
- бэкенд, проверяющий `azp == <свой клиент>`, отвергнет токен обмена (`azp=ruto`)
  — проверить при внедрении;
- выход у провайдера доходит не сразу: выданные C, F и токены ruto доживают свой
  срок (минуты);
- фронты должны жить на поддоменах одного домена, иначе браузер не отдаст куки;
- keycloak-js без правок при каждом открытии страницы идёт на `authorize` —
  переход виден, но провайдер не участвует (ruto отвечает по кукам);
- встраивание приложения в оболочку через iframe: auth-js с расширением входит
  через userinfo и `authorize` не трогает; приложению на keycloak-js в рамке
  нужен `authorize` ruto, а он не должен запрещать показ в рамке (только для
  сайтов из `cors.allow_origins`), иначе вход — переходом всей страницы.

## Риски и как их закрываем

- **ruto отвечает за вход, а не только за маршрутизацию.** Ошибка в брокере —
  дыра в доступе ко всем приложениям: тесты на каждую проверку (клиент, адрес
  возврата, PKCE, срок и повтор кода), официальный набор проверок.
- **Секрет клиента `ruto` — главный ключ.** У провайдера обмен разрешён только
  `ruto` и только для его токенов; позже — подтверждение клиента подписью ключом
  вместо секрета (`private_key_jwt`, RFC 7523).
- **Два слоя токенов.** Логи шлюза показывают, какой токен пришёл (ruto, A, C) и
  какой ушёл бэкенду, значения — маскируются, как сейчас.
- **Одноразовость кода без хранилища.** PKCE и срок 60 с всегда, отметка в Redis,
  если он подключён.
