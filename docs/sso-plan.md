# План: вход через SSO с кукой на шлюзе

Статус: этап 1 сделан, остальные не начаты. Этапы делаются по одному, каждый
заканчивается проверяемым состоянием и ничего не переписывает из предыдущего.

## Цель

Шлюз берёт на себя обмен одноразового кода OAuth (Authorization Code + PKCE) на
токены и держит их в httpOnly-куках. В браузер токены не попадают, фронт в логине
не участвует, бэкенд по-прежнему получает `Authorization: Bearer …` и ничего не
замечает. Проверка токена на каждом запросе — уже существующий метод `jwt`.

Должны одинаково удобно покрываться два сценария:

- один шлюз на все приложения компании и один общий вход (одна кука на
  `api.mdev.kz`, один Keycloak-клиент);
- раздельные входы по приложениям или группам приложений (разные realm'ы,
  разные провайдеры, разные компании на одном шлюзе).

## Решения, принятые заранее

- **Шлюз остаётся без состояния.** Никакого хранилища сессий (Redis, БД, core в
  пути запроса). Всё, что нужно между запросами, лежит в куках: подписанных или
  зашифрованных ключом из конфига, общим для всех подов.
- **Провайдер — единственная новая сущность конфига.** Список `jwt` в Root
  (сейчас только адреса JWK) становится списком провайдеров с именем: адрес JWK,
  настройки входа (Keycloak, клиент, секрет), настройки куки. Метод `jwt` в auth
  ссылается на провайдера по имени. **Ни у App, ни у Endpoint новых полей нет**:
  общий вход или раздельный определяется тем, какого провайдера указали в auth, а
  наследование auth Root → App → Endpoint уже есть.
- **Одна кука на провайдера**, имя `ruto_<провайдер>`. Куки разных провайдеров
  живут на одном хосте и не мешают друг другу.
- **Две куки на сессию:** access-кука с JWT как есть (httpOnly, шифровать нечем
  оправдать, на горячем пути нулевая работа) и refresh-кука, зашифрованная, с
  узким `Path`, чтобы refresh-токен не ездил с каждым запросом и не доходил до
  бэкенда.
- **Служебные маршруты на провайдера, не на приложение:**
  `/_auth/<провайдер>/login|callback|logout|refresh`. Префикс `/_auth/`
  зарезервирован — приложение с таким путём создать нельзя, и маршрут `/*`
  приложения его не перекроет. У каждого Keycloak-клиента один адрес возврата.
- **Горячий путь** получает одну новую ветку: «токен можно взять из куки» плюс
  подстановка `Authorization` бэкенду. Прозрачное обновление токена (этап 5) —
  вторая ветка, отдельная и выключаемая.
- **Разные права при общем входе — это роли, а не отдельный вход.** Метод `jwt`
  уже сверяет роли, в том числе клиентские роли Keycloak
  (`resource_access.<клиент>.roles`). Отдельный провайдер нужен только когда
  различаются источники пользователей.

## Этап 1. Провайдер вместо `jwk_url` и `kid` — сделано

Что меняется:

- запись списка `jwt` в Root получает поле `name` (провайдер);
- метод `jwt` получает поле `provider`; `kid` остаётся необязательным
  ограничением, без него подходит любой ключ из набора провайдера;
- совместимость: имя провайдера необязательно, `provider` у метода тоже; метод
  без `provider` принимает ключ любого провайдера (как раньше по `kid`), нужно
  хотя бы одно из `provider`/`kid`. Старые конфиги работают без правок.
  Провайдер без имени нельзя указать в методе — он только добавляет ключи в
  общий набор. Имена провайдеров уникальны.

Где в коде: модель Root и auth (`internal/domain/root/model`,
`internal/domain/auth/model`), сервис `jwk` хранит ключи по провайдеру,
авторизатор `jwt` берёт ключ по паре «провайдер, kid из токена». Proto, DTO,
админка (поле у провайдера, выбор у метода).

Точка проверки: авторизация по заголовку работает как раньше; после ротации
ключей в Keycloak токены с новым `kid` проходят без правки конфига. Куки нет.

## Этап 2. Токен из куки

Что меняется:

- `ExtractToken` в модели запроса авторизации берёт токен ещё и из куки
  `ruto_<провайдер>` (после заголовка и query-параметра);
- middleware auth при успешной проверке подставляет бэкенду
  `Authorization: Bearer …` и убирает эту куку из заголовка `Cookie`;
- в маски логов добавляются `cookie` и `set-cookie`.

Где в коде: `internal/service/gw/service/auth/model`, middleware auth,
`internal/service/gw/service/logmask`. Больше ничего.

Точка проверки: запрос с `Cookie: ruto_corp=<jwt>` проходит авторизацию, бэкенд
получает `Authorization` и не получает куку, в логах значение замаскировано.
Проверяется curl-ом с токеном, взятым руками из Keycloak. Шлюз пока ничего не
выдаёт.

## Этап 3. Вход: обмен кода и выдача куки

Что меняется:

- у провайдера появляются настройки входа: issuer (адрес Keycloak), клиент,
  секрет, scopes, ключ шифрования куки, публичный адрес шлюза для адреса
  возврата (по умолчанию `base_url` Root);
- маршруты `/_auth/<провайдер>/login`, `/callback`, `/logout`;
- `login`: генерирует state и PKCE verifier, кладёт их в короткую подписанную
  куку, редиректит в Keycloak;
- `callback`: проверяет state, меняет код на токены (один исходящий запрос),
  ставит access-куку (`Path=/`) и зашифрованную refresh-куку
  (`Path=/_auth/<провайдер>`), редиректит на адрес возврата;
- `logout`: гасит куки, при желании зовёт end-session Keycloak.

Где в коде: новый сервисный модуль клиента Keycloak (собрать адрес входа,
обменять код, обновить по refresh; http-клиент с таймаутами по правилам
проекта), маленький модуль «запечатать/распечатать куку», новый обработчик
маршрутов `/_auth/`, который `buildHandler` ставит перед маршрутами приложений.
Горячий путь не трогается, он готов этапом 2.

Точка проверки: настоящий вход через Keycloak, после возврата запросы к
приложениям идут по куке. Через срок жизни access-токена (5 минут по умолчанию)
приходится входить снова. Это уже рабочий SSO без обновления.

Нюансы этапа:

- CORS: для запросов с кукой нужны `allow_credentials=true` и конкретные домены в
  `allow_origins`, звёздочка с куками не работает;
- CSRF: фронт и шлюз на поддоменах одного домена (`app.mdev.kz` / `api.mdev.kz`)
  — один «сайт», `SameSite=Lax` достаточно; чужой домен фронта потребует
  `SameSite=None` и проверки `Origin`;
- размер: access-токен Keycloak 1–2 КБ, лимит куки 4 КБ; лишнее из токена убирать
  mapper'ами в Keycloak;
- аудитория: при общем входе токен выдан клиенту провайдера, бэкенд с строгой
  проверкой `aud` его отвергнет — либо audience mapper в Keycloak, либо бэкенд
  проверяет издателя и подпись;
- срок access-куки в браузере = сроку сессии, а не токена, иначе браузер удалит
  просроченную куку раньше, чем шлюз сможет её обновить.

## Этап 4. Обновление по явной ручке

Что меняется: маршрут `/_auth/<провайдер>/refresh` — читает refresh-куку,
обновляет пару в Keycloak, ставит новые куки. Фронт зовёт его, получив 401.

Где в коде: одна функция в обработчике `/_auth/`, клиент из этапа 3.

Точка проверки: после истечения access-токена вызов `refresh` возвращает новые
куки, сессия живёт столько, сколько живёт refresh-токен.

## Этап 5. Обновление внутри запроса (по желанию)

Что меняется: у провайдера флаг «обновлять прозрачно». Тогда refresh-кука
ставится на `Path=/`, и при просроченном access-токене middleware auth сам зовёт
обновление и ставит новые куки в ответ. Одновременные попытки с одним
refresh-токеном внутри пода склеиваются в один поход в Keycloak
(`singleflight`).

Между подами склейки нет: в Keycloak переиспользование refresh-токена должно
оставаться разрешённым («Revoke Refresh Token» выключен, либо «Refresh Token
Max Reuse» ≥ 2), иначе гонка двух подов разлогинит пользователя.

Это единственный этап, добавляющий логику в горячий путь, поэтому он отдельный и
выключаемый.

Точка проверки: вкладка с десятью параллельными запросами и просроченным
токеном даёт ровно один поход в Keycloak и остаётся залогиненной.

## Этап 6. Хвосты

- ключ server-кэша: при токене из куки `Authorization` подставляется в middleware
  auth, который стоит в цепочке раньше кэша — убедиться, что ключ его видит,
  иначе один пользователь получит ответ другого;
- настройка «без токена отвечать 401 или редиректить на вход» (по умолчанию 401);
- несколько публичных доменов на одном шлюзе: белый список хостов у провайдера,
  адрес возврата из входящего `Host` только при совпадении;
- документация (`overview`, `architecture`), MCP-инструменты ruto знают новые
  поля провайдера.

## Почему это не усложняет код

- Одна новая сущность в конфиге (провайдер), новых полей у App/Endpoint нет.
- Один новый сервисный модуль (клиент Keycloak) и один новый обработчик
  (`/_auth/`); они не знают про приложения, прокси и кэш.
- Middleware auth не ходит в core и хранилища; в худшем случае (этап 5) один раз
  зовёт клиента Keycloak.
- Core не участвует в пути входа: как и сейчас, падение core не мешает шлюзу
  работать на последнем снапшоте.
