# План: вход через SSO с кукой на шлюзе

Статус: этапы 1–4 сделаны, этап 5 отменён, остальные не начаты. Этапы делаются по одному, каждый
заканчивается проверяемым состоянием и ничего не переписывает из предыдущего.

## Цель

Шлюз берёт на себя обмен одноразового кода OAuth (Authorization Code + PKCE) на
токены и держит их в httpOnly-куках. В браузер токены не попадают, фронт в логине
не участвует, бэкенд по-прежнему получает `Authorization: Bearer …` и ничего не
замечает. Проверка токена на каждом запросе — уже существующий метод `jwt`.

Должны одинаково удобно покрываться два сценария:

- один шлюз на все приложения компании и один общий вход (одна кука на
  `api.mdev.kz`, один Keycloak-клиент);
- раздельные входы по приложениям или группам приложений (разные realm'ы,
  разные провайдеры, разные компании на одном шлюзе).

## Решения, принятые заранее

- **Шлюз остаётся без состояния.** Никакого хранилища сессий (Redis, БД, core в
  пути запроса). Всё, что нужно между запросами, лежит в куках браузера.
- **Только стандарт, провайдер заменяем.** Вход — OAuth 2.0 Authorization Code
  с PKCE, адреса ручек провайдера берутся из OpenID Connect Discovery
  (`<issuer>/.well-known/openid-configuration`), клиент представляется
  `client_secret_basic`, выход — RP-Initiated Logout с `id_token_hint`.
  Ничего специфичного для Keycloak в коде нет; требование к провайдеру — выдавать
  access-токен в формате JWT (RFC 9068), что делают Keycloak, Authentik, Zitadel,
  Okta, Auth0 и собственный `id`.
- **Провайдер — в Root, клиент — наследуется Root → App.** Провайдер (`Root.jwt`)
  — это имя, адрес JWK или issuer, внутренний адрес для серверных запросов и
  клиент по умолчанию (`client_id`, секрет, scopes). Приложение
  может указать для провайдера **свой** клиент (`App.jwt`), тогда у него
  отдельный вход и отдельная кука; без своего клиента приложение живёт на общем
  входе Root. У Endpoint новых полей нет. Имя провайдера — наше и постоянное,
  issuer можно менять: при смене провайдера куки и адреса входа у фронтов не
  меняются.
- **Одна кука на единицу входа «провайдер + клиент».** Общий вход: кука
  `ruto_<провайдер>` на `Path=/`. Свой клиент приложения: кука
  `ruto_<провайдер>_<префикс приложения>` на `Path=<префикс>` — она ездит только
  в запросы этого приложения. Куки разных провайдеров и приложений живут на одном
  хосте и не мешают друг другу.
- **Две куки на сессию:** access-кука с JWT как есть (httpOnly, на горячем пути
  нулевая работа) и refresh-кука с узким `Path`, чтобы refresh-токен не ездил с
  каждым запросом и не доходил до бэкенда. В ней же лежит ID-токен для
  стандартного выхода. Обе httpOnly; refresh-кука зашифрована ключом, который
  шлюзы получают от core вместе с настройками (этап 6).
- **Служебные маршруты на единицу входа:** `/_auth/<провайдер>/login|callback|
  logout|refresh` для общего входа и `/_auth/<провайдер>/<префикс приложения>/…`
  для клиента приложения. Префикс `/_auth/` зарезервирован — приложение с таким
  путём создать нельзя, и маршрут `/*` приложения его не перекроет. У каждого
  клиента один адрес возврата.
- **Кука входа (state + PKCE) не подписывается.** Защиту даёт случайность
  значений и сравнение `state` из адреса со `state` из куки: чужую куку в чужой
  браузер не положить. Подпись защищала бы только содержимое, которому мы
  доверяем, а такого нет: адрес возврата проверяется отдельно, срок — `Max-Age`.
  От поддомена-соседа защищает префикс `__Host-` (ставится, когда шлюз на https).
- **Роли при общем входе привязаны к клиенту.** В общем токене лежат роли всех
  клиентов (`resource_access.<клиент>.roles`), поэтому роль в методе `jwt`
  пишется как `клиент:роль` и ищется только у этого клиента. Роль без клиента
  ищется как раньше (в `roles`, `role`, `realm_access.roles` и у любого клиента в
  `resource_access`) — совместимость.
- **Горячий путь** получает одну новую ветку: «токен можно взять из куки» плюс
  подстановка `Authorization` бэкенду. Кука при этом бэкенду тоже уходит: часть
  сервисов может перейти на куки, и они должны работать и так, и так. Обновление
  токена в горячий путь не попадает: его делает фронт через `/_auth/…/refresh`.
- **Разные права при общем входе — это роли, а не отдельный вход.** Свой клиент
  приложению нужен, когда ему нужны собственный `aud`, свой секрет или свой срок
  сессии; отдельный провайдер — только когда различаются источники пользователей.

## Этап 1. Провайдер вместо `jwk_url` и `kid` — сделано

Что меняется:

- запись списка `jwt` в Root получает поле `name` (провайдер);
- метод `jwt` получает поле `provider`; `kid` остаётся необязательным
  ограничением, без него подходит любой ключ из набора провайдера;
- совместимость: имя провайдера необязательно, `provider` у метода тоже; метод
  без `provider` принимает ключ любого провайдера (как раньше по `kid`), нужно
  хотя бы одно из `provider`/`kid`. Старые конфиги работают без правок.
  Провайдер без имени нельзя указать в методе — он только добавляет ключи в
  общий набор. Имена провайдеров уникальны.

Где в коде: модель Root и auth (`internal/domain/root/model`,
`internal/domain/auth/model`), сервис `jwk` хранит ключи по провайдеру,
авторизатор `jwt` берёт ключ по паре «провайдер, kid из токена». Proto, DTO,
админка (поле у провайдера, выбор у метода).

Точка проверки: авторизация по заголовку работает как раньше; после ротации
ключей в Keycloak токены с новым `kid` проходят без правки конфига. Куки нет.

## Этап 2. Токен из куки — сделано

Что меняется:

- авторизатор `jwt` метода с `provider` берёт токен ещё и из куки
  `ruto_<провайдер>` (после заголовка и query-параметра); метод без провайдера
  куку не читает;
- middleware auth при успешной проверке дописывает бэкенду
  `Authorization: Bearer …`, если клиент не прислал свой `Authorization`; кука
  уходит бэкенду как есть;
- в маски логов добавляется `cookie`.

Где в коде: `internal/service/gw/service/auth/model` (разбор куки, отметка
«токен из куки»), авторизатор `jwt`, middleware auth,
`internal/service/gw/service/logmask`, имя куки — `constant.JwtCookieName`.

Точка проверки: запрос с `Cookie: ruto_corp=<jwt>` проходит авторизацию, бэкенд
получает и куку, и `Authorization`, в логах значение куки замаскировано.
Проверяется curl-ом с токеном, взятым руками из Keycloak. Шлюз пока ничего не
выдаёт.

## Этап 3. Вход: обмен кода и выдача куки — сделано

Что меняется в конфиге:

- провайдер в Root (`Root.jwt[]`) получает поля: `issuer` (публичный адрес
  OpenID-провайдера, он же `iss` в токенах; включает discovery и вход),
  `internal_url` (необязательный адрес, по которому шлюз сам ходит к провайдеру
  внутри кластера), `public_url` (адрес шлюза для адреса возврата, по умолчанию
  `base_url` Root) и `client` — клиент по умолчанию: `id`, `secret`, `scopes` (по умолчанию
  `openid`). `jwk_url` при заданном `issuer` необязателен: адрес ключей берётся
  из discovery. Провайдеру с `issuer` имя обязательно;
- приложение получает список `jwt[]`: `{provider, client{id, secret, scopes}}` —
  свой клиент для провайдера. Приложение со своим клиентом принимает только свою
  куку, общую — нет (у неё другие роли и аудитория);
- роль в методе `jwt` может быть записана как `клиент:роль`;
- префикс `_auth` у приложения запрещён.

Что меняется в шлюзе:

- discovery: при применении снимка шлюз запрашивает
  `<issuer или internal_url>/.well-known/openid-configuration`, сверяет
  `issuer` в документе с настроенным и берёт `authorization_endpoint`,
  `token_endpoint`, `end_session_endpoint`, `jwks_uri`. У серверных ручек
  (`token_endpoint`, `jwks_uri`) начало `issuer` заменяется на `internal_url`,
  браузерные остаются публичными. Документ кэшируется, при ошибке живёт прошлый;
- маршруты на каждую единицу входа (провайдер с клиентом по умолчанию —
  `/_auth/<провайдер>/…`, клиент приложения — `/_auth/<провайдер>/<префикс>/…`):
  - `login?redirect=…`: случайные `state`, `nonce` и PKCE verifier кладутся в
    куку входа `ruto-login_<…>` (`__Host-` при https, httpOnly, `SameSite=Lax`,
    10 минут), браузер уходит на `authorization_endpoint` с `code_challenge`
    S256 и `nonce`;
  - `callback`: сверяет `state`, меняет код на токены одним запросом
    (`client_secret_basic`, `code_verifier`), проверяет ID-токен так, как
    требует OpenID Connect Core §3.1.3.7 (подпись ключом провайдера, `iss`,
    `aud` и `azp` — наш клиент, `exp`, `nonce` из куки входа; без ID-токена
    вход отклоняется, scope `openid` запрошен всегда), проверяет подпись, `iss`
    и `exp` access-токена по ключам провайдера, ставит access-куку (JWT как есть) и
    refresh-куку `ruto-rt_<…>` на `Path=/_auth/<…>` с refresh-токеном и
    ID-токеном (base64url от JSON), перенаправляет на адрес возврата;
  - `logout?redirect=…`: гасит обе куки и уводит на `end_session_endpoint` с
    `id_token_hint` и `post_logout_redirect_uri` (если ID-токена нет — сразу на
    адрес возврата);
- адрес возврата разрешён, если он относительный, или его origin совпадает с
  `public_url`, или подходит под запись `cors.allow_origins` — точную или
  шаблон поддомена `https://*.mdev.kz` (`*` не считается). Иначе 400 — чтобы
  не было открытого редиректа;
- флаг `Secure` у кук — по схеме `public_url`; срок access- и refresh-куки —
  `refresh_expires_in` ответа провайдера, иначе сутки.

Где в коде: `internal/infra/httpx` (фабрика http-клиентов с таймаутами),
`internal/service/gw/service/oidc` (discovery с кэшем, обмен кода, обновление по
refresh), `internal/service/gw/handler/http/authflow` (маршруты `/_auth/`,
регистрируются в `buildHandler` до маршрутов приложений), `jwk` берёт `jwks_uri`
из discovery, имя куки метода `jwt` вычисляется при наследовании
(`AuthMethodJWT.CookieName`), роли `клиент:роль` в авторизаторе `jwt`. Горячий
путь не меняется, он готов этапом 2. Админка: поля провайдера и раздел «клиенты
входа» у приложения; MCP: новый секрет `client.secret` в масках.

Точка проверки: настоящий вход через провайдера, после возврата запросы к
приложениям идут по куке. Через срок жизни access-токена (5 минут по умолчанию)
приходится входить снова. Это уже рабочий SSO без обновления.

Что нужно на стороне провайдера (Keycloak):

- клиент шлюза — конфиденциальный («Client authentication: On»), с адресом
  возврата `https://api.mdev.kz/_auth/<провайдер>/callback` и адресом после
  выхода (`Valid post logout redirect URIs`) — адресами фронтов;
- для общего входа с ролями по приложениям: у клиента шлюза «Full scope
  allowed», приложения заведены клиентами-контейнерами ролей (вход у них
  выключен), роли назначаются пользователям или группам. В токене тогда есть
  `resource_access.<приложение>.roles` и `aud` с этими клиентами;
- для своего клиента приложения — обычный конфиденциальный клиент с адресом
  возврата `https://api.mdev.kz/_auth/<провайдер>/<префикс>/callback`.

Нюансы этапа:

- CORS: для запросов с кукой нужен `allow_credentials=true`. Middleware CORS
  при `*` отдаёт браузеру origin запроса, так что кука технически едет и с
  `*`, но тогда запрос с кукой пользователя может сделать любой сайт. Для кук
  в `allow_origins` лучше точные домены или шаблон поддоменов
  `https://*.mdev.kz` — он пускает `shop.mdev.kz`, `admin.mdev.kz` и любые
  новые админки, но не чужие сайты. Адреса возврата входа разрешает тот же
  список, `*` там не учитывается (открытый редирект); `*` остаётся как было,
  как открывать доступ — решает человек;
- CSRF: фронт и шлюз на поддоменах одного домена (`app.mdev.kz` / `api.mdev.kz`)
  — один «сайт», `SameSite=Lax` достаточно; чужой домен фронта потребует
  `SameSite=None` и проверки `Origin`;
- размер: access-токен 1–2 КБ, лимит куки 4 КБ; лишнее из токена убирать
  mapper'ами; refresh-кука с ID-токеном после base64 — около 3 КБ;
- выход через `end_session_endpoint` гасит всю SSO-сессию провайдера: куки
  других единиц входа в браузере останутся, их access-токены доживут свой срок,
  а обновление уже не пройдёт;
- срок access-куки в браузере = сроку сессии, а не токена, иначе браузер удалит
  просроченную куку раньше, чем шлюз сможет её обновить.

Не вошло в этап (отложено): настраиваемое имя claim с ролями для провайдеров,
которые кладут роли не в `resource_access` (сейчас читаются `roles`, `role`,
`realm_access.roles`, `resource_access.*.roles`). Ручка `me` для фронта —
сделана позже, см. «Ручка `me`» после этапа 4.
Ключи в JWKS: RS256/384/512, PS256/384/512, ES256/384/512 (P-256/384/521) и
EdDSA (Ed25519) — сделано позже, `jwk/keys.go`; HS* не принимаются, им нужен
секрет провайдера.

## Этап 4. Обновление по явной ручке — сделано

Что меняется: у каждой единицы входа маршрут `POST /_auth/<провайдер>[/<префикс>]/refresh`
— читает refresh-куку (она уже ограничена `Path=/_auth/<…>`, так что доезжает
сюда и никуда больше), обновляет пару у провайдера (`oidc.Refresh`,
`grant_type=refresh_token`, `client_secret_basic` клиентом единицы), проверяет
новый access-токен так же, как при входе, и ставит обе куки заново. Фронт зовёт
его, получив 401, и повторяет запрос:

```js
const r = await fetch(url, { credentials: 'include' })
if (r.status === 401) {
  const rr = await fetch('https://api.mdev.kz/_auth/corp/refresh', { method: 'POST', credentials: 'include' })
  if (rr.status === 204) return fetch(url, { credentials: 'include' })
  if (rr.status === 401) location.href = 'https://api.mdev.kz/_auth/corp/login?redirect=' + encodeURIComponent(location.href)
}
```

Ответы:

- `204` — куки обновлены. Срок обеих — `refresh_expires_in` нового ответа, иначе
  сутки. Провайдер, который не меняет refresh-токен, не присылает его в ответе —
  в куке остаётся прежний; ID-токен при обновлении необязателен — остаётся прежний
  (он нужен для выхода). Присланный проверяется как при входе, кроме `nonce`
  (OpenID Connect Core §12.2): подпись, `iss`, `aud`/`azp`, `exp` и тот же `sub`,
  что у ID-токена сессии; иначе `502`, куки не трогаются;
- `401` — сессии нет: refresh-куки нет или провайдер ответил `invalid_grant`
  (refresh-токен истёк, отозван, сессия в провайдере закрыта). Пора на `login`.
  Куки при этом **не гасятся**: параллельное обновление тем же токеном из другой
  вкладки могло только что поставить свежие, а браузер применяет ответы в порядке
  прихода — гашение затёрло бы их;
- `502` — провайдер недоступен или отказал по другой причине (неверный секрет
  клиента и т. п.), куки не трогаются, выходить из сессии пользователю незачем.

У всех ответов `Cache-Control: no-store`.

Решения этапа:

- только `POST`: кука `SameSite=Lax` не едет в межсайтовом POST, так что чужой
  сайт не может заставить браузер обновить сессию; `GET` отвечает 405. Запрос
  без тела и своих заголовков — «простой» для CORS, preflight не нужен, но
  origin фронта должен быть в `cors.allow_origins` и `allow_credentials=true`,
  иначе браузер не отдаст ответ скрипту;
- одновременные обновления одним refresh-токеном внутри пода (несколько вкладок
  получили 401 разом) склеиваются в один поход к провайдеру (`singleflight` в
  `oidc.Refresh`) и получают один и тот же ответ; поход доживает до конца, даже
  если начавший его запрос оборвался. Ещё `oidc.RefreshGrace` (15 с) ответ
  отдаётся повторно на тот же refresh-токен — запросы, отправленные до того, как
  браузер получил новые куки. Ответ общий, его не меняют: недостающие поля
  обработчик дописывает в копию;
- склейка между подами — через Redis (см. ниже). Без Redis каждый под ходит к
  провайдеру сам, и при включённой ротации refresh-токенов в Keycloak («Revoke
  Refresh Token») проигравший гонку получит 401, но куки не тронет (см. выше).

Склейка между подами через Redis. Шлюз по-прежнему не хранит сессий: в Redis
на `oidc.RefreshGrace` (15 с) лежит только ответ провайдера на одно обновление,
горячий путь Redis не трогает.

- адрес даёт core: env `GW_REDIS_ADDR`, `GW_REDIS_DB`, `GW_REDIS_PASSWORD`; без
  `GW_REDIS_ADDR` — Redis самого core (`REDIS_*`); нет ни того, ни другого —
  склейка только внутри пода. Core отдаёт настройки шлюзам в `Snapshot.Get`
  (поле `gateway`), в БД, админку и MCP они не попадают. `Snapshot.GetVersion`
  несёт `settings_version` — HMAC настроек ключом `ADMIN_JWT_SECRET` (версия
  видна в REST, по простому хэшу слабый пароль можно было бы подобрать). Шлюз
  сверяет обе версии; сменились только настройки — переподключает Redis, не
  пересобирая маршруты. Старый core полей не шлёт — шлюз работает без Redis;
- обновление: под смотрит в Redis готовый ответ на этот refresh-токен (ключ —
  `ruto:gw:refresh:<sha256(token endpoint, клиент, refresh-токен)>`, сам токен в
  имени ключа не виден). Нет — берёт блокировку `SET NX` (срок — таймаут
  запроса к провайдеру плюс 2 с), идёт к провайдеру, кладёт ответ на 15 с и
  снимает блокировку. Не взял — раз в 25 мс смотрит, не появился ли ответ;
  блокировка, пережившая свой срок (держатель умер), отдаётся следующему.
  Отказ провайдера не запоминается: ждущие по очереди спросят его сами;
- Redis недоступен — под обновляет сам, как без Redis, с предупреждением в
  логе. Значения в Redis не шифруются (вопрос шифрования — этап 6).

Итог: на один refresh-токен со всех подов — один поход к провайдеру, ротацию в
Keycloak можно включать.

Где в коде: `authflow.(*unit).refresh` и общий с `callback` `setSession`
(`internal/service/gw/handler/http/authflow/handlers.go`), маршрут в
`authflow.go`, склейка в `internal/service/gw/service/oidc/client.go` и
`shared.go` (Redis), настройки шлюзов — `snapshotModel.GatewaySettings`,
`usecase/snapshot`, `gw/core_client`. Горячий путь не меняется.

Точка проверки: после истечения access-токена вызов `refresh` возвращает новые
куки, сессия живёт столько, сколько живёт refresh-токен. Покрыто тестами
`authflow` (ротация, провайдер без ротации, `invalid_grant`, недоступный
провайдер, клиент приложения) и `oidc` (склейка одновременных обновлений).

## Ручка `me`: кто вошёл — сделано

Зачем: токены в браузер не попадают, и фронту неоткуда узнать, кто вошёл и с
какими ролями, кроме как спросить шлюз. У каждой единицы входа маршрут `me`:
читает access-куку этой единицы (только её — не `Authorization`: у клиента с
bearer-токеном claims и так есть), проверяет её так же, как при входе (подпись
ключом провайдера, `iss`, `exp`) и отдаёт **payload access-токена как есть**,
JSON-объектом.

Где лежит: **под путём access-куки** — `<путь куки>/_auth/<провайдер>/me`.
Для общего входа кука на `Path=/`, и `me` там же, где остальные маршруты
единицы: `GET /_auth/<провайдер>/me`. Для клиента приложения кука ограничена
префиксом приложения (`Path=/<префикс>`) и до `/_auth/…` не доезжает — браузер
просто не шлёт её туда, так что `me` рядом с `login`/`refresh` отвечал бы 401
при живой сессии (поймано на стенде с Keycloak). Поэтому у приложения `me`
внутри его префикса: `GET /<префикс>/_auth/<провайдер>/me`; остальные маршруты
единицы остаются на `/_auth/<провайдер>/<префикс>/…`. Сегмент `_auth` в начале
`http.path` endpoint'а зарезервирован, как и в начале `path_prefix`.

Ответы (у всех `Cache-Control: no-store`):

- `200` — claims токена целиком, включая произвольные (`tenant_id`, `groups`
  и т. п.). Шлюз ничего не выбирает и не переименовывает: провайдеры кладут
  логин и роли в разные места (`preferred_username`/`upn`/`login`,
  `roles`/`realm_access`/`resource_access`), а фронту часто нужна своя claim —
  любой маппинг пришлось бы расширять под каждого. Это не утечка: payload и так
  уходит бэкендам, здесь его видит владелец сессии, а подпись остаётся в
  httpOnly-куке — из одних claims токен не собрать и никуда не предъявить;
- `401` — куки нет, она не разбирается, подписана не провайдером или просрочена.
  Фронт реагирует как на любой 401: `POST …/refresh`, потом повтор.

Единица входа приложения читает свою куку (`ruto_<провайдер>_<префикс>`), общая
— `ruto_<провайдер>`; чужая кука — 401. Запрос — «простой» GET с куками, preflight
не нужен; origin фронта должен быть в `cors.allow_origins` с
`allow_credentials=true`, как и для `refresh`.

Где в коде: `authflow.(*unit).me` и `parseAccessToken` (общий с проверкой при
входе и обновлении) в `handlers.go`, маршрут — `mePath` в `authflow.go`,
резерв `_auth` в `endpointModel.Http.Normalize`. Покрыто тестом `TestMe` (нет
куки, мусор, просроченный, чужая подпись, bearer не читается, claims отдаются
как есть, `me` приложения внутри префикса и по своей куке).

Точка проверки (стенд: Keycloak 26.4 в docker, два статических фронта на
разных портах, срок access-токена 60 с): вход через общий клиент → `me` отдаёт
claims с ролями и своей claim `tenant_id`; через минуту `me` → 401 → `refresh`
204 → повтор 200 с новым `exp`; приложение со своим клиентом входит через ту же
SSO-сессию без пароля, его `me` на `/<префикс>/_auth/<провайдер>/me` отвечает
по куке приложения.

## JS SDK для фронтов — сделано

Зачем: каждый фронт иначе повторяет одно и то же — куки в запросах, после `401`
обновление и повтор, одно обновление на все вкладки, разбор ролей из claims.
Пакет `sdk/js` (`@rendau/ruto-auth`, описание — `sdk/js/README.md`) делает это
один раз, без зависимостей, и не привязан к HTTP-клиенту: в проектах компании
в ходу axios, ofetch/`$fetch` (Nuxt), ky и голый fetch.

- Ядро: `createRutoAuth({ gateway, provider, app? })` — адреса единицы входа,
  `me()`, `refresh()` (одна склейка на вкладку, Web Lock между вкладками),
  `run(request)` — универсальный «повторить после 401» для любой библиотеки
  (статус читается из `Response`, ответов/ошибок axios, ofetch, ky, XHR),
  `fetch` — готовая обёртка, `login()`/`logout()`. `onLoginRequired` — один
  вызов на обновление, сказавшее «сессии нет»; `me()` его не трогает.
- Адаптеры отдельными entry: `./axios` (интерсепторы), `./ofetch` (хук
  `onResponseError` + собственный retry ofetch), `./ky` (`afterResponse`,
  сигнатуры ky 1 и 2). Библиотеки не являются зависимостями — типы структурные.
- Помощники по claims: `rolesOf`, `hasRole` (правило шлюза: `client:role` —
  только у этого клиента, голая роль — где угодно), `usernameOf`.
- Браузерная сборка `dist/ruto-auth.iife.js` (глобал `RutoAuth`) для страниц
  без сборщика. Её отдаёт сам шлюз: `GET /_auth/ruto-auth.js` на любом шлюзе
  (файл собирается в образ шлюза, `docker/Dockerfile.gateway`; путь
  переопределяется `SDK_JS_FILE`). Фронт знает только хост шлюза, и версия
  скрипта всегда совпадает с версией шлюза, на который он ходит. Файл читается
  при старте, копии gzip и brotli считаются один раз на максимальном уровне;
  браузер получает `Vary: Accept-Encoding`, сильный `ETag` на каждую кодировку
  (`If-None-Match` → 304) и `Cache-Control: public, max-age=300,
  stale-while-revalidate=86400` — страница не ждёт скрипт, а новая сборка
  доезжает за минуты (`internal/service/gw/handler/http/sdkjs`). Тестовые
  фронты стенда берут скрипт оттуда.

Точка проверки: тесты `sdk/js` (ядро, роли, адаптеры на настоящих axios,
ofetch и ky); стенд с Keycloak — общий вход, вход приложения со своим клиентом
без пароля, прозрачное обновление после истечения access-токена, выход, три
одновременных `401` после выхода → одно обновление и один `onLoginRequired`.

`prompt` у `login` — сделано. `GET …/login?redirect=…&prompt=login` передаёт
провайдеру параметр `prompt` из OpenID Connect Core §3.1.2.1 как есть: `login`
— спросить учётные данные заново даже при живой SSO-сессии (после отказа в
доступе входит другой человек, иначе провайдер молча вернёт того же),
`select_account` — выбор аккаунта, `consent` — экран согласия, `none` — без
взаимодействия. Несколько значений через пробел, `none` только одно; что-то
вне стандарта — 400 до похода к провайдеру. В SDK —
`auth.login(redirect, { prompt: 'login' })`. Покрыто `TestLoginPrompt` и тестом
SDK.

Возврат ошибки входа на фронт — сделано. Раньше неудачный `callback` (провайдер
ответил отказом, не сошёлся `state`, обмен кода не удался, токен не прошёл
проверку) заканчивался текстом на хосте шлюза, и человек застревал на голой
странице, а фронт ничего не узнавал. Теперь, если адрес возврата известен (кука
входа на месте и адрес проходит `returnUrl`), шлюз отправляет браузер на него с
`auth_error=<код>` в query (фрагмент `#/…` hash-роутера сохраняется). Стандарт
описывает только, как провайдер сообщает об ошибке шлюзу (`error`,
`error_description` на `redirect_uri`, RFC 6749 §4.1.2.1); этот отрезок — наше
соглашение, коды взяты стандартные, где они есть: код провайдера как есть
(`access_denied`, `login_required`, …), `invalid_grant` и прочие отказы
token endpoint, `temporarily_unavailable` — провайдер недоступен; свои —
`state_mismatch` и `invalid_token` (ID- или access-токен не прошёл проверку).
Код, не похожий на код (не `[A-Za-z0-9_.-]`, длиннее 64), заменяется на
`server_error`, чтобы в адресную строку фронта не попало что попало. Без куки
входа возврат некуда — остаётся текст, как раньше. В SDK — `loginError()`
читает код из адреса страницы. Покрыто `TestLoginFailureGoesBackToTheFront`.

## Этап 5. Обновление внутри запроса — отменён

Задумывался так: у провайдера флаг «обновлять прозрачно», refresh-кука на
`Path=/`, и при просроченном access-токене middleware auth сам обновляет сессию.
Был сделан и убран: refresh-токен тогда едет с каждым запросом на хост шлюза, а
по нему можно бесконечно получать новые access-токены. Бэкендам он бы не уходил,
но светился бы в каждом запросе (логи балансировщиков, прокси, любые точки по
пути). Вариант «сессии в Redis, а в браузере только ключ сессии» решал бы это,
но делает шлюз хранилищем сессий; отложен.

Решение: обновляет фронт сам — получив 401, зовёт `POST /_auth/…/refresh`
(этап 4) и повторяет запрос. Refresh-кука остаётся на `Path=/_auth/<…>` и в
обычные запросы не попадает. Пример обёртки с одним обновлением на вкладку и
`navigator.locks` между вкладками — в описании этапа 4.

От этапа осталось то, что полезно и без него:

- прокси вырезает из запроса к бэкенду куки шлюза — `ruto-rt_…` и
  `ruto-login_…` (`__Host-` тоже); access-кука остаётся (решение этапа 2).
  Кука входа лежит на `Path=/` и раньше уходила бэкендам;
- browser-кэш с `public` отдаёт ответ, в котором есть `Set-Cookie`, как
  `private`: общий кэш перед шлюзом не должен раздавать чужие куки;
- повторная выдача ответа на тот же refresh-токен (`oidc.RefreshGrace`), теперь
  15 с и со склейкой между подами через Redis — описано в этапе 4.

## Этап 6. Хвосты

- ключ server-кэша: закрыто этапом 2 — `Authorization` подставляется в
  middleware auth, который стоит раньше кэша, и ключ его видит;
- шифрование refresh-куки — сделано. Ключ не в конфиге провайдера, а в
  настройках шлюзов от core (как Redis): core выводит его (HKDF-SHA256, 32 байта)
  из env `GW_COOKIE_SECRET`, а без него — из `ADMIN_JWT_SECRET`, и отдаёт в
  `Snapshot.Get` (`gateway.cookie_key`); ключ входит в `settings_version`, так
  что все поды получают его одновременно и без пересборки маршрутов
  (`gw.applySettings` → `authflow.SetCookieKey`). Кука — AES-256-GCM поверх JSON
  с refresh- и ID-токеном, имя куки подмешано как associated data: значение
  одной единицы входа в куку другой не подложить. Не расшифровалось (чужой или
  сменившийся ключ, порча) — сессии нет: `refresh` отвечает 401, `logout` гасит
  куки без `id_token_hint`. Core без ключа (старый) — шлюз предупреждает в логе
  и refresh-куку не ставит: вход работает, обновления нет. Смена секрета
  разлогинивает всех из сессий шлюза (access-куки доживают свой срок). Ключ
  в админке и MCP не виден — это внутренний секрет шлюза, не настройка;
- настройка «без токена отвечать 401 или редиректить на вход» (по умолчанию 401);
- несколько публичных доменов на одном шлюзе: белый список хостов у провайдера,
  адрес возврата из входящего `Host` только при совпадении;
- документация (`overview`, `architecture`), MCP-инструменты ruto знают новые
  поля провайдера.

## Почему это не усложняет код

- Одна новая сущность в конфиге (провайдер) плюс необязательный свой клиент у
  приложения; у Endpoint новых полей нет.
- Один новый сервисный модуль (клиент OpenID-провайдера) и один новый обработчик
  (`/_auth/`); они не знают про приложения, прокси и кэш.
- Middleware auth не ходит в core, хранилища и к провайдеру.
- Core не участвует в пути входа: как и сейчас, падение core не мешает шлюзу
  работать на последнем снапшоте.
